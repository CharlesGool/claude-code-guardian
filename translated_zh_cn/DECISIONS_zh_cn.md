## 2026-09-12 — 会话以非特权账户运行，这正是 `--dangerously-skip-permissions` 得以成立的前提

- **背景：** 操作者要求受监督的会话以一个普通的、可免密 `sudo` 的账户运行，
  而不是 root，并配合 `claude --dangerously-skip-permissions`。这两半其实是
  同一个请求：`claude` 在以 root 身份运行时会拒绝这个参数并立即退出，所以
  只要会话属于 root，能用的最强"永不停下来询问"设置就只有
  `--permission-mode auto`。这个拒绝行为，正是 2026-08-21 记录为 v0.7.0
  真正回归问题的那个：一个设置要求 `bypassPermissions` 的 root 实例会
  崩溃循环。
- **决策：** 新增 `RUN_AS_USER`（全局，默认 `root`）。root 依然负责安装和
  监督；tmux 服务端、`claude` 本身以及监督循环都以该账户运行。`install`
  会采用 `$SUDO_USER`。出厂的 `CLAUDE_ARGS` 默认值变为
  `--dangerously-skip-permissions --remote-control`，root 安装时例外，
  取而代之的是 `--permission-mode auto --remote-control`。这种不可能的
  组合会被 `install`、`new` 和 `run` 在入口处直接拒绝。
- **为什么是全局而不是按实例：** 每个实例共享同一个 tmux 服务端
  （2026-08-17 的决策），而一个 tmux 服务端只能属于一个账户。按实例分账户
  就需要一个账户对应一个服务端，那正是此前已经被否决过的设计。
- **为什么用 `passwd` 而不是 `$HOME`：** 在 `sudo` 下执行的管理命令拿到的
  是 root 的 `$HOME`。所有由此派生的路径——工作目录、`~/.claude/sessions`、
  `~/.claude/projects`——都会指向 root 的文件，而会话用的却是另一个账户。
  同样的道理也迫使 `claude` 的位置及其登录状态必须通过 `runuser` 来解析，
  而不是在调用者自己的 shell 里解析："claude 是否已登录？"这个问题问的是
  某个账户的状态。
- **为什么默认值仍是 `root`：** 一台已存在的主机通过重新运行 `install` 来
  升级，而 `install` 从来不会改写已有的配置文件。任何别的默认值都会把一台
  正在运行的主机的会话迁到另一个账户下，而那些对话不会跟着一起迁过去。
- **有意接受的代价：**
  - 账户切换不会带走对话。`claude` 会把记录留在旧账户的 `~/.claude` 下，
    新账户读不到，而记录目录又是以工作目录命名的，通常两者会同时变化。
    迁移是一套写好文档的手工步骤，不是工具自动完成的事。
  - 该工具现在会替 `claude` 首次运行时的信任提示做出应答（默认选中的是
    **No, exit**，所以此前那种盲目发送 Enter 的做法，只会把每个新会话都
    杀掉，再把它重生进同一个死循环）。替操作者按下"是"，是代替他们做出的
    一个决定；理由是 `$WORKDIR` 是他们为一个无人值守会话专门配置的目录。
    这一行为和那个屏幕当前的措辞是绑定的——措辞一改，重生循环就会卷土
    重来，而日志上只会显示 `claude exited`。
  - 把 `--dangerously-skip-permissions` 作为出厂默认值，等于把账户的全部
    权限交给会话，包括在一个可免密 `sudo` 的账户上等同于 root 权限。这是
    操作者自己该权衡的取舍，而 root 安全的替代方案只需要改一行配置。
- **在做这件事的过程中发现、并在同一版本里修复的问题：** 每一个 tmux
  目标都是裸的会话名，而 tmux 会退化成前缀匹配。当 `claude-code` 和
  `claude-code-work` 同时存在时，指向前者的命令会落到后者头上——包括
  `send-keys`，也就是说 `/remote-control` 和裸 Enter 会敲进另一个实例正在
  进行的对话里。目标现在都是精确匹配（会话目标用 `=name`，窗格和窗口目标
  用 `=name:`；两者都已针对 tmux 3.2a 验证过）。这个问题在本版本之前就
  可能出现，但本版本让它变得很容易出现，因为 `install` 会在已有实例旁边
  再建一个 `claude-code` 实例。
- **同样是实测中发现的：** 套接字文件的生命周期会超过创建它的那个 tmux
  服务端。切换账户之后，遗留下来的、属主为 root 的套接字会让每一次创建
  会话都以 `Permission denied` 失败，而日志上只会显示 `claude` 退出了。
  `install` 现在会在没有服务端应答这个套接字时把它删掉，而在仍有服务端
  应答时不去碰它。

## 2026-08-23 — 会话不可达故障已经查清；它重新打开了 v0.7.0 的撤回

- **背景：** 操作者再次报告了那个由来已久的症状——某个会话在网页端显示
  `(no content)`，桌面客户端卡在 `connecting`，手机端却声称
  `connected`，而通过 SSH 直接 attach 却一切正常，唯独所有远程客户端都
  不行。此前一直认为这在主机端无法诊断（"这里没有任何东西能检测到那种
  状态"）。那个判断是错的，而且这个工具在那个错误判断之下表现得比
  没有它还糟。
- **在动手之前，实测直接观察到的现象：**
  - 两个互不相关的实例几乎在同一秒记录了 `remote control disconnected`，
    各自被发送了一次 `/remote-control`，三秒之后监督端记录的 URL 竟然和
    断线之前**一模一样**。真正的重新建立会铸造一个新 id，说明这次什么都
    没有重建——但记录却当作成功。
  - 亲手操作 TUI 解释了这一点：对一个自认为仍处于连接状态的会话执行
    `/remote-control`，只会打开一个提示对话框（`Disconnect this session` /
    `Show QR code` / `Continue`），什么都不会重建。**监督端唯一的修复
    动作，恰恰在最需要修复的那个状态下是无效的。**
  - 在那个对话框里先选 `Disconnect this session`，再执行
    `/remote-control`，才会真正重连并铸造一个新 id。这条修复路径是存在
    的。
  - `bridgeSessionId` 在一次真正的重连过程中会**发生变化**，所以它可以作为
    成功的有效证明——但只能以"发生了变化"为准，绝不能以"非空"为准。
  - 这个故障会自我锁死：`claude` 只在状态发生变化时才重写它的会话文件，
    所以一次失败的修复之后，那个陈旧的非空 id 会一直留在那里（被抓到时
    已经滞留了 6.2 小时），而那个 5 秒一次的检查会永远读到"已连接"。日志
    保持干净，这正是这个问题此前看起来无法察觉的原因。
  - 在这张网络里，主机端的 TCP 状态不是一个可靠的健康信号：出站流量会经过
    一个透明代理，所以在对端已经断开之后，客户端套接字仍会保持
    ESTABLISHED，因为保活包是被代理应答的。两个互不相关的实例几乎同一秒
    掉线，指向的是这条共享路径本身，而不是任何单个会话的问题。
- **决策：** 把这一点记为**这个工具**的一个已确认缺陷，并将修复它列为
  待办事项中的头等大事。诚实地划清责任：掉线本身不是这个工具造成的
  （它同样会发生在一个不受此工具监督的 `claude` 身上），但一直处于故障
  状态是这个工具的责任——修复动作本身是无效的，而它的成功判据又是重新
  读取一个在修复什么都没做的情况下根本不可能变化的值。
- **这一条直接关系到下面 2026-08-21 的撤回决定。** 那条撤回 v0.7.0/v0.8.0
  的条目当时记录说，那个决定性的实验还没有做。现在它已经做了，而结果
  指向了相反的方向：v0.7.0 的两个核心机制——要求以*变化后*的 bridge id
  作为证明、以及先拆除再重建——恰恰是今天的证据表明所需要的东西。
  **这条条目并不推翻那个决定**；那次撤回还移除了其他东西，而且操作者
  尚未确认新 URL 能否在远程客户端上端到端地真正工作。它记录的是：撤回
  当时所依据的前提已经不再成立，因此恢复那批被打包保存下来的引用必须
  重新评估，而不能就此当作已经结案。
- **被否决的方案：**
  - **把 `claude-guardian url` 也当作有问题的部分** —— 在同一次调查中被
    怀疑过，随后被排除：它读取的是当前存活的会话文件，也正确地跟上了
    新的 id。去修一个没坏的东西只会掩盖真正坏掉的那一个。
  - **归咎于透明代理并到此为止** —— 它确实最可能是触发因素，但这个工具
    理应能在自己控制不了的触发因素面前依然存活。一个无法修复问题的修复
    机制，本身就是缺陷，无论是什么把连接打断的。
  - **靠重启 `claude` 来恢复** —— 这确实有效，但相比对话框那套操作序列，
    这是一把大得多的锤子，而且重启后恢复对话是一套独立的机制，有它自己
    的故障模式。一旦修复机制真正生效，就不再需要这个手段。
- **已验证：** 上述每一项发现都是在一个存活实例上直接观察到的——那个
  提示对话框及其选项、成功的"先 `Disconnect` 再 `/remote-control`"重连、
  发生变化的 `bridgeSessionId`，以及 `url` 跟踪到新值。尚未验证的是：新
  铸造的 URL 是否真的能从一个远程客户端驱动该会话。那是操作者需要做的
  测试，也是上面那次重新评估的前置条件。

## 2026-08-21 — 强制执行"至少一个会话"这条底线，并默认开启

- **背景：** 操作者问，如果一台主机上所有常驻会话都被关闭了，重启之后
  会不会自动带回来一个。答案是不会。下面 2026-08-16 那条条目记录的创立
  需求是"至少始终有一个可用"，v0.1.0 的更新日志也写着这个工具"始终保持
  至少一个可远程接入的 Claude Code 会话存活"——但自从 v0.2.0 转向多实例
  模板化之后，就再也没有任何机制真正强制执行这一点。这是自然发生的：
  `install` 会启用默认实例，systemd 会启动任何被启用的实例，但没有人
  归档过最后一个实例。`archive`（禁用 + 删除配置）和 `deactivate`（仅
  禁用）都会在没有任何检查、没有任何警告的情况下把实例数量降到零；促成
  这个问题的那台主机，在 v0.7.0/v0.8.0 撤回之后正好就处于这种状态，重启
  之后什么都不会起来。
- **决策：** 两个机制，刻意分开。
  (A) 当被移除的实例是唯一一个会在开机时启动的实例时，`archive`/
  `deactivate` 会发出警告——除非带了 `--yes`，否则还会询问。
  (B) 一个 `oneshot` 单元，`claude-guardian-floor.service`，每次开机运行
  一次 `ensure-floor`，在没有其他实例会启动的情况下重新创建并启动默认
  实例。新增设置 `ENSURE_DEFAULT_INSTANCE`，**默认为 `1`**。
- **为什么默认开启：** 引发这次讨论的问题本身就是"它不是理应会带回一个
  吗？"——把它默认关闭，会让每一个没有去读配置文件的人的这份期待落空。
  一个整体存在意义就是"始终有一个会话可达"的工具，不应该把这个保证做成
  需要主动开启的选项。退出这个保证的开关是存在的，而且在三处文档里都有
  说明，这才是正确的顺序。
- **靠 `is-enabled` 计数，而不是靠配置文件计数：** `deactivate` 会把配置
  文件留下来，所以如果靠数 `$INSTANCES_DIR/*.env` 的数量，会把那些永远
  不会启动的实例也算进去。这条底线问的是真正重要的那个问题——systemd
  实际上会拉起多少个单元。
- **接受的后果：** 在 `ENSURE_DEFAULT_INSTANCE=1` 时，停用*最后*一个实例
  这个操作会在下一次开机时被撤销，这和 `deactivate` 自己"不会在开机时
  重启"的承诺相矛盾。这个保证优先，而 `deactivate` 现在会在动手之前把
  这一点大声说出来。一台真的打算以空闲状态开机的主机，应该设置
  `ENSURE_DEFAULT_INSTANCE=0`；这和"把所有实例都停用"不是同一个操作，
  而把这两者混为一谈，正是当初造成"静默归零"这种状态的原因。
- **被否决的方案：**
  - **只做警告（只有 A，没有 B）** —— 操作者问的是重启会发生什么，而一个
    警告对一台已经处于零实例状态的主机毫无作用——而这台主机当时正是
    如此。
  - **在每一次监督循环上都持续运行的底线检查** —— 这会在一次刻意的
    `archive` 操作之后几秒钟就重新创建一个实例，让 `archive` 变得无法
    使用。每次开机运行一次，才是既符合承诺（"能扛过一次重启"）又不会
    和操作者对着干的节奏。
  - **把这条底线折叠进实例模板单元里** —— 模板的那些单元只对已经启用的
    实例存在，所以在唯一需要修复的那种状态下，其中没有一个会运行。它
    必须是自己独立的一个单元。
  - **在底线逻辑内部执行 `systemctl enable --now`** —— 在开机事务内部
    等待另一个单元的启动任务完成，存在死锁风险；`enable` 加上
    `start --no-block` 能达到同样的结果而不会阻塞。
  - **复用版本号 `v0.7.0`** —— 那个标签和 `v0.8.0` 都曾经被推送后又被
    删除。任何拉取过其中任一个的人，如果再拉一次，会在同一个名字下拿到
    不同的代码，这正是发布规则禁止移动已发布标签的原因。这次发布使用的
    是 `v0.9.0`；`v0.7.0` 和 `v0.8.0` 保持作废状态。
- **已验证：** shellcheck 干净；在一个沙箱路径树里针对一个 stub 版
  `systemctl`/`claude` 跑了一套 48 个用例的独立测试（底线为零/为一/为
  二/所有实例都被停用/主动关闭该功能这几种情况；`archive` 和
  `deactivate` 各自在两种设置下、有 `--yes` 和无 `--yes`、在非 tty 和 pty
  下的警告行为；`--yes` 的处理；install/uninstall/purge 对单元的接线；
  以及对 `list`/`archives`/usage 的回归测试）。同一套测试跑在 v0.6.2
  基线上会有 48 个用例中的 27 个失败，说明它确实能检测出这项工作"不存在"
  的情况，而不只是单纯附和已经做完的工作——这正是下面 v0.6.1 那次缺陷
  留下的教训。之后又在维护者本人的主机上、用真实的 systemd 实测过一遍：
  `install` 写入并启用了底线单元；停用唯一的那个实例在不带 `--yes` 时被
  拒绝，带上之后给出了警告；在零实例状态下启动底线单元把该实例带了回来
  （真实的 `claude` 进程、tmux 会话正常、没有开机死锁）；再次启动它时
  记录的是 `already enabled — nothing to do`，也没有创建出第二个会话。
- **未做实测的部分：** 实例配置文件完全缺失的那条分支（也就是 `archive`
  走过的那条路径）——沙箱测试覆盖了它，但在实机上 `archive` 被一个权限
  分类器拦下，没有想办法绕过去。也没有真的做过一次重启；底线单元是通过
  直接启动来验证的，而这正是 systemd 在开机时会走的同一条代码路径。

## 2026-08-21 — 撤回 v0.7.0 和 v0.8.0；代码基线回退到 v0.6.2

- **背景：** 四个受监督的实例，以及另外一个这个工具没有监督的普通
  `claude`，在闲置一段时间后全都从 claude.ai 变得不可达（"Can't reach
  your computer"）。在记录到的第一次掉线之前，监督端日志在长达十一个
  小时的窗口期内是干净的，这正是这个项目从 v0.6.0 起就一直在追查的
  故障模式。
- **决策：** 维护者判断 v0.7.0 那次 Remote Control 重构就是原因，于是
  撤回了它。已安装的二进制回滚到了 v0.6.2；`v0.7.0` 和 `v0.8.0` 这两个
  标签在本地和远程都被删除，`v0.7.0` 的 Release 对象被删除，两个版本的
  快照目录都被移除，`main` 被强制重置到 `v0.6.2`。此后所有工作都从
  v0.6.2 这个基线重新开始。
- **为什么（维护者本人的判断）：** 掉线现象是从 v0.7.0 上线之后才开始
  出现的，在 v0.6.2 上没有观察到过。
- **针对这一判断记录下来的反面证据，避免以后凭记忆重新争论一遍：**
  (1) 同样的掉线现象也发生在一个在 tmux 之外独立运行的普通 `claude`
  身上，而当时零个受监督的实例存在，这个工具的任何版本都不可能对一个
  它没有在监督的进程造成掉线；(2) v0.7.0 自己的更新日志把"一个实例可能
  在日志干净的情况下无限期地不可达"列为它*修复*了的一个缺陷——而那正是
  v0.6.2 的行为，所以这次回滚等于把它恢复了回来；(3) v0.7.0 真正的
  回归问题，是从 `CLAUDE_ARGS` 里去掉了 `--permission-mode auto`，这会
  让一个设置要求 `bypassPermissions` 的 root 实例陷入崩溃循环，而
  v0.8.0 当时已经修好了恰恰这个问题。这次决定是在这三点都摆在桌面上的
  情况下做出的。
- **这次撤回的代价：** `reconnect` 命令、那套 23 个用例的独立 Remote
  Control 测试、`REMOTE_CONTROL_MAX_BRIDGE_AGE_SEC`（唯一能从上游静默
  死掉的 bridge 中自动恢复的机制），以及 `BACKLOG.md`。在有替代方案之前，
  一个不可达会话唯一的补救办法就是手动 attach 上去敲
  `/remote-control`。
- **同样在这次学到、并且不会随这次决定过期的一点：** bridge id 在重启
  之后依然存活。一个被杀掉的实例用 `claude --resume` 带回来之后，会
  重新挂接到*同一个* `bridgeSessionId` 上，所以 claude.ai 的 URL 不会
  变（在四个实例上都验证过）。所以这个 id 不能被当作"有东西正在流动"的
  证明来读，一次重启之后 URL 没变也不是什么异常症状。
- **尚未解决、也是这条条目存在的原因：** 在做出删除决定的时候，那个
  决定性的实验还没有做——让一个实例闲置一整晚，看看 v0.6.2 是不是也会
  掉线。如果会，那问题的根源就是 Remote Control 这条链路本身，而不是
  这个工具，被撤回的那些工作就值得找回来；一份包含每一个被删除引用的
  完整打包已经提前做好了，位置记在维护者本人的本地笔记里。如果不会，
  上面那个判断就得到了确认，问题应该去 v0.7.0 的 diff 里找。

## 2026-08-17 — 每一个监督周期都检查连接状态，并且默认不再自动应答对话框

- **背景：** v0.4.0 带着三个实例上线还不到一个小时，操作者就报告了
  "怎么其他两个会话都disconnected了"。两个实例确实都真的断线了
  （`bridgeSessionId: null`），但在其他方面都运行正常——存活、正在
  对话中，只是从 claude.ai 上无法连接。没有任何东西真的坏掉：监督端
  每隔一个 `REMOTE_CONTROL_REFRESH_SEC`（1200 秒）才检查一次，而其中
  一个实例恰好在我们正盯着看的时候，于下一次检查时自愈了。这*本身*就是
  问题所在。同一次调查还揭示了另外一半：那个实例的日志里有三行
  `sending Enter`——那个无人值守的提醒机制，替操作者应答了他们刚从
  claude.ai 打开、还没来得及自己去应答的确认对话框。
- **决策（连接方面）：** 检查现在每一个监督周期都会运行
  （`REMOTE_CONTROL_CHECK_SEC`，默认 5 秒 = `CHECK_INTERVAL_SEC`），而
  重连动作本身则用自己的计时器做限流（`REMOTE_CONTROL_RECONNECT_BACKOFF_SEC`，
  默认 60 秒）。`REMOTE_CONTROL_REFRESH_SEC` 被移除，如果配置里还设着这个
  值会在启动时给出警告。
- **为什么：** 1200 秒这个数字是从 v0.2.0 继承下来的，当时它的含义是
  "每隔多久重新发一次 `/remote-control` 来保持连接存活"。v0.3.0 证明了
  这个假设是错的，把这个检查改成了被动式，却保留了这个数字——于是一个
  最初为"按键间隔"选定的数值，就悄悄变成了"一个实例最多可以不可达多久"。
  单纯读一个文件不花任何代价，也不会敲任何按键；从来就没有理由把它做得
  很慢。把两个计时器分开正是让这一切安全的关键：只有重连动作才会触碰
  会话本身，所以只有重连才需要限流。那个退化情况（根本没有可用的会话
  文件，所以永远无法确认是否成功）保留了一个慢得多的内部 1200 秒重试，
  否则它会永远不停地往那个会话里敲 `/remote-control`。
- **决策（提醒方面）：** `UNATTENDED_NUDGE_SEC` 默认改为 `0`——除非操作者
  明确开启，否则监督端不会替用户应答任何确认对话框。
- **为什么：** v0.4.0 的假设是"没有 tmux 客户端连着 + 停在一个对话框上
  超过整个时间间隔"是"已被放弃"的一个好的代理指标。生产环境证明这个
  假设不成立：Remote Control 本身不是一个 tmux 客户端，所以一个正在用
  手机看着某个对话框的操作者，和一个已被放弃的会话，在这个指标上是
  分辨不出来的，而 Enter 会接受当前高亮的任何选项。被否决的替代方案：
  拉长这个时间间隔（只是缩小了触发窗口，故障模式本身没变，还拖慢了
  真正的自愈恢复）；只把"已连接"的 Remote Control 视为"有人能来应答"，
  只在断线状态下才提醒（这依然是在猜——一个已连接的会话完全可能已经被
  放弃了，而且这也不会改变这次事故的结果，因为当时两个实例都处于断线
  状态）；保持开启但把文档写得更详细（v0.4.0 当时已经写了文档，结果还是
  让写文档的那个人自己也感到意外）。这个功能本身保留下来，带着它那个
  仅在 `waiting` 状态下才生效的限制，留给那些更希望实例能自我解困的
  操作者——只是它不再是默认选项。
- **后果：** 一个被放弃、停在某个对话框上的实例，现在会一直停在那里，
  直到有人来应答它。这正是预期的取舍：监督端的职责是保持会话*可达*，
  而不是替会话里的事情做决定。

## 2026-08-17 — 跨越重启恢复对话，而不是开一个空白的新对话

- **背景：** 在 v0.3.0 已经运行了一段时间之后，操作者的报告是："重启后
  恢复的也没有记录啊，所以没什么意义"——这些实例重启之后确实回来了，
  但每一次都是一个空白的对话，所以真正保留下来的是*进程*，而不是*工作
  内容*。这原本被记录为 v0.3.0 的一个已知问题；生产环境的使用让它变成了
  两个已知问题里更重要的那一个。
- **实际发生的情况：** `respawn-pane` 会复用窗格原始的命令行，所以一个
  崩溃的 `claude` 会以同一个 `--session-id` 重新起来——这条路径一直都
  没问题。重启是另一回事：它会把 tmux 服务端一起带走，所以
  `create_session` 会被执行，而它无条件地铸造了一个新的 `uuidgen` id。
  这一点在操作者的主机上得到了确认：重启前的对话记录完好地保存在磁盘上
  （4.6 MB，最后一次写入是在重启前七分钟），只是变成了孤儿。
- **决策：** `create_session` 现在会优先使用该实例自己上一次的
  `claude_session_id`——这个值已经记录在状态里，供 `archive`/`resume`
  使用——并以 `claude --resume <id>` 启动，前提是该对话的记录文件仍然
  存在于 `$CLAUDE_PROJECTS_DIR` 下。优先级顺序：先是显式的
  `RESUME_SESSION_ID`（来自 `resume <archive-id>`），然后是该实例自己
  上一次的对话，最后才是一个新 id。`RESUME_AFTER_RESTART=0` 会恢复此前
  的旧行为。
- **被否决——无条件恢复，不检查记录文件是否存在。** 这样能少一个对内部
  目录结构的依赖，但它会把一个 `claude` 可能从未听说过的 id 硬塞给它，
  而故障模式是静默然后致命的：`claude` 立即退出，监督端每隔
  `CHECK_INTERVAL_SEC` 就重建同一条会失败的命令，这个实例就再也回不来
  了。先检查一下的代价只是一次 `[ -r ]`。
- **被否决——使用 `claude --continue`（恢复这个工作目录下最近的一次
  对话）。** 完全没有对记录文件路径的依赖，但"这个 cwd 下最近的一次"
  并不等于"这个实例自己的那一次"：两个共享同一个 `WORKDIR` 的实例，或者
  操作者手动在那里跑过的任何一次对话，都会被错误的那个实例接管。实例
  身份必须来自这个工具自己记录的状态。
- **被否决——恢复时带上 `--fork-session`。** 这样能让每次开机的历史各自
  独立、便于阅读，但代价是牺牲了本来要解决的那个需求：跨越重启的一段
  连续对话。
- **接受的代价：** 记录文件的路径（`$CLAUDE_PROJECTS_DIR/<把工作目录中
  每一个非字母数字字符替换成 - 之后的结果>/<id>.jsonl`）是 Claude Code
  的一个内部实现细节，已经针对 2.1.202 验证过，和 `bridgeSessionId` 属于
  同一类风险。缓解方式也一样：这条路径是可配置的，一旦读不到，就会
  退化成开一个新对话，而不是直接失败。需要留意的故障模式是无声的——
  一旦这个约定发生了变化，每一次重启都会悄悄地重新变回空白对话。
- **同样接受的一点：** `claude` 出于其他某种原因拒绝了这次 `--resume`。
  `create_session` 会在启动几秒钟之后检查一次该会话是否已经死掉——或者
  根本没能启动起来，因为 `remain-on-exit` 只有在 `new-session` 返回之后
  才会被设置，所以一次极快的退出会把整个会话一起带走——一旦确认，就会
  改用一个新对话重试。这后半部分是被独立测试发现的，正是这项检查存在
  的意义所在——防止陷入无限循环的那个 bug。
- **对操作者而言的后果：** 已经在实机上观察到、值得知道的一点是——因为
  `claude` 的会话 id 没有变，实例的 `claude.ai/code/...` URL 在测试中
  也扛过了重启。这是 Remote Control 绑定会话方式带来的一个副作用，
  不是一个承诺；继续用 `claude-guardian url <name>` 去获取这个 URL。

## 2026-08-17 — 只提醒真正停在对话框上的会话，而不是那些看起来像"无人值守"的会话

- **背景：** v0.3.0 的第二个已知问题。`UNATTENDED_NUDGE_SEC` 会每隔
  300 秒，向任何没有 tmux 客户端连接的实例发送两次 Enter。Remote
  Control 本身不算一个 tmux 客户端，所以一个操作者正在从 claude.ai
  操作的会话也符合这个条件——停在一个空闲提示符上时是无害的，但它也
  完全可能替用户应答一个确认对话框。
- **决策：** 把这个提醒动作和 Claude Code 自己在
  `$CLAUDE_SESSIONS_DIR/<pid>.json` 里的 `status` 字段挂钩。已经在
  2.1.202 上实测观察到三个取值：`busy`（正在处理一轮对话）、`idle`
  （空闲的提示符）、`waiting`（停在一个确认对话框上）。只有
  `waiting` 状态才会被输入内容，而且只有在 `statusUpdatedAt` 显示这个
  对话框已经无人应答超过 `UNATTENDED_NUDGE_SEC` 之后才会触发——所以
  倒计时是从对话框出现的那一刻开始的，而不是监督端恰好看了一眼的那
  一刻。这也让这个提醒机制变得更有用了：它只会在那个它本来就是为之
  设计的状态下触发，而不是靠一个定时器，大多数时候打在那些根本没什么
  需要清理的会话上。
- **被否决——改用 `updatedAt`（最后一次活动时间）来判断。** 最先尝试的
  方案，一开始看起来是对的，但拿一个真实会话一测就露馅了：维护者自己的
  实例已经处于一轮对话中间长达二十分钟，`updatedAt` 却依然是二十分钟前
  的值，因为这个字段追踪的是状态*切换*，不是正在进行中的工作。用它来
  判断，恰恰会把 Enter 敲进这项改动本来是要保护的那个会话里。
- **被否决——只要 Remote Control 处于连接状态就跳过提醒。** 用 v0.3.0
  已经在读的数据实现起来很容易，但每个实例默认都带着
  `--remote-control`，所以这样会在所有地方都关掉提醒，而不是把它
  收窄。
- **接受的代价：** 一个在 claude.ai 上打开了对话框、却因为还打算去应答
  而拖了超过 `UNATTENDED_NUDGE_SEC` 时间的人，和一个已被放弃的会话，
  在这个机制下是分辨不出来的，依然会被替他应答掉。调节这个时间间隔是
  唯一的调节手段。当没有可用的会话文件时，会退回到 v0.2.0 的按墙钟计时
  的旧行为作为兜底。

## 2026-08-17 — MAX_SESSIONS 默认为 0（无上限）

- **背景：** 操作者踩到了 `MAX_SESSIONS=3`，并把它理解成了这个工具本身
  的限制——"对话为什么有3个限制，我实测可以开很多啊?"——这是一个错误的
  心智模型：这个上限从来只作用于受 guardian 监督的实例，从未作用于
  Claude Code 本身。
- **决策：** 默认 `MAX_SESSIONS="0"`，表示无上限，同时这个上限对任何
  想设置它的人依然可用。`0` 必须被明确赋予这个含义；在此之前，`0` 会
  拒绝掉每一个实例，因为原来的检查只是一个裸的 `count >= MAX_SESSIONS`。
- **被否决——彻底移除这个设置。** 它背后关心的成本问题是真实的（每个
  实例都是一个独立的 `claude` 进程和 token 预算）；真正出错的地方在于
  默认就给所有人强加了一个数字。
- **后果：** 已有的部署会保留它们 `config.env` 里已经写着的任何值——
  `install` 刻意从不覆盖它——所以这项改动只会影响全新安装拿到的默认值。

## 2026-08-17 — 从 claude 自己的会话文件读取 Remote Control 状态，而不是抓取终端内容

- **背景：** 操作者在生产环境报告了两个症状：会话在闲置一段时间之后，
  claude.ai 上显示"已断开"，以及每次重启后都会多出一个对话。对这两点
  的调查揭出了四个不同的问题，其中三个出在这个工具本身。
- **实际出错的地方：**
  1. **v0.2.0 那套保活机制什么用都没有。** 它相信重新执行一次
     `/remote-control` 就能刷新连接，于是每隔
     `REMOTE_CONTROL_REFRESH_SEC` 就重跑一次。针对真实二进制验证过：
     当 Remote Control *已经*处于开启状态时，`/remote-control` 只会
     打开一个提示对话框（"Disconnect this session" / "Show QR code" /
     "Continue"）。它什么都不会重新建立。所以当连接真的断开时，
     根本没有任何东西去修复它——而这正是被报告的那个症状。
  2. **抓取 URL 的方式可能抓到别人的 URL。** 它会在整个可见窗格里搜索
     `https://claude.ai/code/session_...`，取最后一个匹配。这一点是在
     实机上被抓到的：`claude-code` 实例的屏幕上显示着另一个实例的 URL
     （操作者当时正在那里调试），刷新动作把*那个* URL 写进了
     `claude-code` 的状态里，于是 `claude-guardian url claude-code`
     返回的是一个指向另一个对话的链接。任何恰好显示在屏幕上的会话
     URL——一条 commit trailer、某条命令的输出——都可能造成这种情况。
  3. **"无人值守"这个判断标准用错了。** Remote Control 本身不是一个
     tmux 客户端，所以一个正在被人类通过 claude.ai 操作的实例看起来
     像是无人值守的，那次定期注入的 `/remote-control` 就*落进了那段
     正在进行的对话里*，成了一轮用户输入。
  4. 不算这个工具的 bug：一个 v0.2.0 验证阶段遗留下来的 `test` 实例
     还处于启用状态，导致开机时启动了两个实例。已归档。
- **决策：** 停止从终端内容推断 Remote Control 的状态。Claude Code 会为
  每一个正在运行的会话写入 `$CLAUDE_SESSIONS_DIR/<pid>.json`，其中的
  `bridgeSessionId` 字段在连接期间保存着 Remote Control 的会话 id，
  断开之后变为 `null`；一个实例的 `claude` 就是它 tmux 窗格的命令，
  所以 `#{pane_pid}` 能直接得到那个文件的名字。读它来回答"是否仍然
  连接？"和"URL 是什么？"这两个问题。`REMOTE_CONTROL_REFRESH_SEC` 的
  含义也相应改变：它现在表示这项检查多久运行一次，而只有当检查结果
  显示连接确实已经断开时，才会发送按键。在一个健康的实例上，监督端
  现在完全不会敲任何东西进去。
- **被否决——继续抓取终端内容，但把正则表达式锚定到
  `/remote-control` 的输出上。** 这能修好"抓到错误 URL"这个 bug（事实
  上也确实被保留下来，作为 Claude Code 不写会话文件时的兜底方案），但
  它修不好真正的问题：它依然需要往会话里敲东西才能获知任何信息，所以
  它没办法在不打扰一段可能有真人在场的对话的前提下，区分"已连接"和
  "已断开"。
- **被否决——通过状态栏里的 `/rc` 指示符来检测连接状态。** 那个指示符
  来自操作者自己的 `claude-hud` 状态栏插件，不是 Claude Code 本身提供
  的，所以它只会在一台机器上生效。
- **被否决——每次检查都无条件重连。** 简单，而且总能保持最新，但每一次
  重连都会铸造一个新的 `claude.ai/code/...` URL（实测验证：在一个原本
  没被碰过的会话上，经历一次断开/连接循环之后 id 发生了变化），所以
  这会每 20 分钟就把 URL 换一次，却毫无好处。改为只在真正断开时才重连。
- **接受的代价：** `bridgeSessionId` 是 Claude Code 的一个内部实现细节，
  不是一个承诺的接口，已经针对 2.1.202 验证过。用三种方式缓解：这个
  路径是可配置的（`CLAUDE_SESSIONS_DIR`）；读取时会和该实例自己的
  `pid` 以及记录的 `claude_session_id` 做交叉核对，这样一个被复用的
  PID 就不会返回别人的会话；一个读不到的文件会退化成 v0.2.0 的抓取
  方式，而不是直接失败。
- **对操作者而言的后果：** 一次重连会改变实例的 URL，所以这个 URL 是
  一个需要按需获取的东西（`claude-guardian url <name>`），而不是一个
  可以收藏的书签。这一点已经写进了 README 和 DESIGN。

## 2026-08-17 — 推翻 2026-08-16 的"单一默认会话"：加入具名的、可并发的多实例支持

- **背景：** 操作者真实的工作方式演变成了希望同时拥有若干个各自独立、
  并发受监督的 `claude` 对话（例如每个项目一个），每一个都能单独远程
  控制，并且能够暂停（"取消激活"）或永久归档某一个而不影响其他——这些
  都是原来那套单实例设计做不到的。在动手实现之前，先在实机上验证了：
  一个 claude.ai 账户*确实*可以同时承载不止一个并发的
  `--remote-control` 会话（操作者当时已经在手动这样做了）——这正是下面
  2026-08-16 那条决策留下的唯一一个未解决的技术疑问（"如果操作者以后
  需要同时运行不止一个 Claude 实例，再重新考虑这一点"）。
- **决策：** 把 systemd 单元改造成一个模板
  （`claude-guardian@<name>.service`），完全按照当时 DESIGN.md 里
  "How to extend" 一节所勾勒的方式来做。一个 tmux 服务端（一个
  `TMUX_SOCKET`），多个具名会话——tmux 本身原生就支持这一点，所以不需要
  为每个实例单独开一个套接字。每个实例的配置存放在
  `/etc/claude-guardian/instances/<name>.env`（只覆盖
  `WORKDIR`/`CLAUDE_ARGS`/`CLAUDE_BIN`）；`TMUX_SOCKET`、
  `CHECK_INTERVAL_SEC`、`REQUIRED_APT_PKGS`、`UNATTENDED_NUDGE_SEC`、
  `REMOTE_CONTROL_REFRESH_SEC`，以及新增的 `MAX_SESSIONS` 依然是全局、
  整机共享的开关——针对这些设置做按实例区分并不是一个真实存在的需求，
  硬加上去只会让配置面翻倍，却换不来任何被要求过的好处。
- **随这次推翻一并加入的新能力：**
  - `new` / `activate` / `deactivate`：分别用于创建、恢复监督、以及在
    不杀掉会话本身的前提下暂停监督。`deactivate` 被刻意和 `archive`
    区分开来——操作者要求的是"取消激活"（暂停）和"归档"两个分开的、
    一个非破坏性一个破坏性的操作。
  - `archive` / `resume` / `archives` / `rm-archive`：操作者确认归档
    应当在保存状态之后**杀掉**存活的 claude 进程（而不只是取消激活并
    让它继续运行）——见下面"归档会杀掉进程"这条子决策。
  - 现在每个实例在创建时都会带上一个 `claude --session-id <uuid>`
    （通过 `uuidgen` 生成，因此 `uuid-runtime` 被加进了
    `REQUIRED_APT_PKGS`），而不是把它留成隐式的，这样做具体是为了让
    `archive` 能够记录下磁盘上哪一份对话记录
    （`~/.claude/projects/<escaped-cwd>/<uuid>.jsonl`）属于哪一个实例，
    也让 `resume` 能把同一个 id 传回给 `claude --resume <uuid>`。这一点
    已经直接验证过：`claude --help` 确实暴露了 `--session-id`、
    `--resume`、`--fork-session` 这几个参数；对话记录也确实存放在那个
    路径下（已针对本机自己的 `~/.claude/projects/-root/*.jsonl` 确认
    过）。
  - claude.ai 的远程控制 URL（`https://claude.ai/code/session_...`）
    现在会在每个实例启动之后立即从 tmux 窗格里抓取（并在每次无人值守的
    `/remote-control` 刷新时重新抓取一次），存进按实例保存的状态里，
    这样 `claude-guardian url <name>` / `list` 就能直接打印出来，完全
    不需要人手动 attach 上去——这正是操作者明确提出的目标（"以后都不
    需要终端"）。已实机验证：在 `/remote-control` 执行之后，文本
    `https://claude.ai/code/session_...` 确实出现在
    `tmux capture-pane -p` 的输出里。
- **子决策——归档会杀掉进程，而不只是取消激活：** 已经明确向操作者
  求证过（直接问了：是只取消激活，还是先抓取记录再杀进程）。理由是：
  一个被"归档"的实例应该释放它的 tmux 窗格和进程资源，而不是永远
  暂停在那里、继续占用和 `MAX_SESSIONS` 相关的资源限制；滚动缓冲区和
  `claude_session_id` 会在杀进程之前保存到
  `/var/lib/claude-guardian/archive/`，专门为了确保对话内容不会有任何
  丢失。
- **被否决的方案：**
  - **保持单实例，让操作者自己手动运行第二份不相关的工具副本** ——
    这违背了 guardian 存在的意义：第二份副本将得不到任何监督、不会
    自动重生、没有无人值守的保活机制，也无法纳入统一的
    `list`/`archive` 体系。
  - **每个实例一个 `TMUX_SOCKET`**（每个实例一个 tmux 服务端）——tmux
    本身已经能在一个服务端上多路复用多个会话；每个实例再开一个服务端，
    只会增加运维负担（要跟踪 N 个套接字、维持 N 个服务端存活），却
    换不来任何新能力。
  - **一个基于 REST/HTTP 的生命周期控制 API** —— 操作者的诉求是基于
    CLI/remote-control 的（"不需要终端"指的是不需要 SSH 进去，而不是
    要替换掉 CLI 本身，CLI 依然是通过工具自己的命令、从一个远程
    `claude` 会话里驱动的）；加一个面向网络的控制面，会为一个单操作者、
    单主机的工具，带来一个既没被要求过、又巨大的攻击面增量。
- **后果：** 每一个此前不需要带实例参数的、已有文档记录的命令
  （`attach`、`logs`、`start`、`stop`、`restart`、`status`）在不带任何
  参数时依然可用，默认指向 `claude-code` 这个实例，所以一个已有的
  v0.1.0 部署，其肌肉记忆式的命令在升级之后依然可用。`install` 在一台
  已有的 v0.1.0 主机上，会禁用/移除旧的非模板化单元，并在新模板下
  （`claude-guardian@claude-code.service`）重新启用同一个 tmux
  会话——新旧两个单元里都有 `KillMode=process`，意味着这只会停掉监督
  *循环*本身，绝不会停掉 tmux 服务端或其中的 `claude` 进程，所以一段
  正在进行中的对话能扛过这次升级。`purge` 的影响范围从"一个会话"扩大
  到了"每一个存活的实例"——它现在会打印出存活实例的数量，并要求交互式
  确认（或者带上 `--yes`）才会继续执行，而且刻意让
  `/var/lib/claude-guardian/archive/` 保持原样（归档必须通过
  `rm-archive` 显式删除），这样一次彻底的清理就永远不会悄悄毁掉一份
  已归档的对话。

## 2026-08-16 — `install` 在 claude 未登录时强制拒绝；登录检查改为 `claude auth status`

- **背景：** 用户要求一项登录检查，要求在 Claude Code 尚未登录的情况下
  真的能阻止安装继续进行（此前，缺少登录只会在 `install` 和 `run` 两处
  产生一个警告）。
- **决策：**
  - 发现 `claude auth status`（JSON 输出，`loggedIn` 字段）是一个真实、
    权威的认证检查方式——已直接验证：已登录时退出码为 0，在一个隔离
    出来、没有任何凭据的 `HOME` 下退出码为 1。凡是检查登录状态的地方，
    都用它取代了原来那套基于文件是否存在的启发式判断（检查
    `~/.claude/.credentials.json` 之类的文件），因为一份陈旧或失效的
    凭据文件在旧的启发式判断下会被判定为通过，实际上却根本无法使用。
  - 新增了 `require_login()`，只在 `cmd_install` 里被调用，一旦
    `claude auth status` 失败就 `die`——已经用一个伪造的、处于未登录
    状态的 `HOME` 做了端到端验证，`cmd_install` 会拒绝执行，也不会写出
    任何配置文件。
  - `preflight_enforce`（`run` 和 `install` 共用）保留原有的非阻塞行为，
    只是现在用的是更准确的检查方式。
- **被否决：** 把这个强制拦截也折进 `preflight_enforce` 本身——这样会
  导致 `run`/正在运行的 systemd 服务，在一次成功安装之后如果登录状态
  丢失，也会强制失败——这超出了实际被要求的范围（当时明确问的是关于
  *安装*的场景），而且会把一个本可恢复的状况（通过 `attach` 重新登录）
  变成一个已经正常工作的部署陷入重启失败循环。
- **后果：** 现在 `install` 要求 `claude auth login`（或者任何其他已经
  完成的登录方式）必须先发生——先部署好 guardian、再通过 `attach`
  交互式登录的做法不再可行；登录必须排在前面。

## 2026-08-16 — 首次运行和无人值守提醒都发送两次 Enter（而不是一次）；新增 `purge` 命令

- **背景：** 用户报告说，第一次部署时需要按两次 Enter 才能让 `claude`
  到达它正常的提示符（大概率是一个引导/信任确认屏幕），并要求以后始终
  发送两次——他指出，在已经处于正常提示符状态时多敲一次 Enter 也不会
  有任何代价。另外还单独要求了一个真正彻底的卸载方式，要求它能移除
  所有东西，而不只是 systemd 服务本身。
- **决策：**
  - `create_session` 现在会在启动 `claude` 之后立刻发送两次 Enter
    （间隔一秒），而不再单纯依赖那个无人值守提醒的计时器最终去清掉
    首次运行的那个屏幕。
  - `nudge_enter` 现在也改为发送两次 Enter 而不是一次，出于同样的
    理由——已经用一个真实的功能测试（一个统计 stdin 行数的伪造进程）
    验证过，两条路径都精确发送两次按键，时机也正确，并且完整的
    `supervise_loop` 会在正确的那一次周期触发它们。
  - 新增了 `claude-guardian purge`：停止/禁用/移除 systemd 单元（和
    `uninstall` 一样），另外还会杀掉 tmux 服务端，并移除配置目录和
    已安装的二进制文件。`uninstall` 本身没有变化——依然是那个安全的、
    日常维护用的命令，会保留存活的会话和配置不动；`purge` 是新增的、
    显式的、刻意具有破坏性的"移除一切"命令。
  - 在做这项改动的过程中，还顺带发现并修复了一个潜藏的 bug：`usage()`
    用了一个写死的 `sed -n '2,25p'` 行号范围，而在之前的某次提交加入
    GPL 头部之后，这个范围早就已经悄悄过期了（没有任何报错），导致
    打印出错误的帮助文本。改成了按模式匹配的范围
    （`/^# Usage:/,/^#   run /p`），这样就不会因为对上面那段头部的
    编辑而再次跑偏。
- **被否决：** 尝试在决定要发送几次 Enter 之前，先去检测当前屏幕具体是
  哪一种（信任对话框、引导流程，还是已经处于正常提示符）——这样带来的
  脆弱性，不值得用来换取的那点好处，因为多发一次无害的 Enter 已经能
  达到同样的效果。同时也否决了直接修改 `uninstall` 原有行为，而不是
  新增一个独立的 `purge` 命令——保持安全默认值（不动会话本身）是一个
  刻意设计、也已经过测试的特性，值得和一次彻底的清理明确区分开来。
- **后果：** `purge` 会无条件杀掉任何存活的 claude 会话——这一点已经在
  文档里明确写出，作为它和 `uninstall` 之间的区别。这个命令没有针对
  实机上真实的 systemd 单元做端到端测试（那样做会摧毁正在生产环境运行
  的部署）；它是靠代码走查，以及复用已经经过测试的 `cmd_uninstall`
  模式，加上对这个工具自己拥有的那些路径
  （`/etc/claude-guardian`、`/run/claude-guardian`、已安装的二进制
  文件）直接做 `rm -rf` 来验证的。

## 2026-08-16 — 把 CLAUDE_BIN 解析为绝对路径，不要相信 systemd 自己的 PATH

- **背景：** 在第二台主机上执行的一次全新 `install` 成功了，但服务
  立刻进入了 `failed` 状态。`preflight_enforce` 里的
  `command -v "$CLAUDE_BIN"` 检查在 `install` 过程中交互式运行时完全
  正常，但当 systemd 自己去执行 `claude-guardian run` 时却失败了——
  systemd 默认的 PATH
  （`/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin`）
  不包含 `~/.local/bin`，而这正是典型的 npm/pip 用户级安装中
  `claude` 所在的位置。本机自己的部署恰好掩盖了同一个潜藏的 bug，
  因为这台机器上还有第二个 `claude` 位于 `/usr/bin/claude`（一个诱饵），
  所以这个问题此前从未在这里暴露出来。
- **决策：** 分两部分修复，都用真实的功能测试验证过（而不只是代码
  走查）：(1) `write_default_config` 现在会在安装时通过 `command -v`
  解析 `CLAUDE_BIN`——使用的是安装程序自己那个拥有完整 PATH 的交互式
  shell——并把解析出来的绝对路径直接写进
  `/etc/claude-guardian/config.env`，所以全新安装不会再遇到这个问题。
  (2) `preflight_enforce`/`preflight_report` 现在会在直接查找失败时，
  退回去通过 `bash -ic "command -v claude"` 来解析 `claude`，所以那些
  已经安装、配置里还写着裸字符串 `"claude"` 默认值的主机，会在下一次
  `run`/`check` 时自动自愈，不需要手动去改配置文件。
- **被否决：** 用 `bash -lc`（login，非交互式）作为这个兜底机制——
  已经测试确认这条路径**不**管用：Debian 默认的 `~/.bashrc` 一开头
  就是 `[ -z "$PS1" ] && return`，这一行会在任何非交互式调用下触发，
  包括 `bash -l`，所以在还没执行到 `PATH=` 那一行之前就已经返回了。
  `bash -ic`（交互式）才是真正能让 bash 设置 `$PS1`、并把
  `~/.bashrc` 剩下的部分跑完的方式——这是这版修复第一版之所以行不通的
  真实的、经过测试确认的原因，不是一个假设。
- **后果：** `bash -ic` 在非 tty 环境下会向 stderr 打印一些
  作业控制/终端相关的警告（无害，会被丢弃——已经验证过这些噪音不会
  混进被捕获的 stdout 值里）。每一次 `preflight_enforce` 调用，现在
  在快速路径失败时都有可能额外派生出一个交互式 shell——而这只会发生
  在 `CLAUDE_BIN` 本来就无法直接解析的情况下——代价可以忽略不计，而且
  只出现在失败路径上。

## 2026-08-16 — 始终可远程控制：`--remote-control` 作为默认值，无人值守自动 Enter 作为一项明确接受的取舍

- **背景：** 用户报告最初的设计在"始终可远程控制"这一点上做得还不够

- **决策：**

    `--permission-mode auto --remote-control`。已经实机验证过
    `--remote-control` 确实会打印出一个可以从网页/手机端控制的
    `claude.ai/code/...` URL，独立于 SSH——这现在是主要的远程控制
    路径，SSH + `tmux attach` 作为兜底方案（DESIGN.md 的
    Goals/Architecture 部分已相应更新）。
  - 在 `supervise_loop` 里新增了一套仅在无人值守时才生效的保活机制：
    当 `tmux list-clients` 显示没有任何客户端连接时，在
    `UNATTENDED_NUDGE_SEC`（默认 300 秒）之后发送一次裸 Enter，用来
    清除 `auto` 模式退化时可能出现的确认对话框，并在
    `REMOTE_CONTROL_REFRESH_SEC`（默认 1200 秒）之后重新执行一次
    `/remote-control`，赶在 Anthropic 官方文档里那个大约 30 分钟的
    "could not reach the Remote Control server" 阈值之前刷新连接。
    信息来源：`claude --help`（参数确实存在，已在本机验证）、
    Anthropic 的 `remote-control.md` 和 `permission-modes.md` 文档
    （30 分钟阈值、auto 模式的退化行为——来自查阅资料，未做过独立的
    端到端复现）。
  - 这套自动 Enter 机制在第一次部署时**被 Claude Code 自己的 auto
    模式分类器实机标记**了出来（"在没有明确用户授权的情况下，绕过了
    人在回路中的安全兜底机制"）——它会接受当前无论高亮/默认的是哪个
    选项，而不知道那对于那个具体的提示来说是不是安全的选择。这个取舍
    已经明确摆到了用户面前（自动 Enter 相对于更可预测、但需要更多前期
    配置的 `--permission-mode dontAsk` + `permissions.allow` 方案）；
    用户确认按照最初的要求，继续使用自动 Enter。
- **被否决：** `--permission-mode dontAsk` 配合一份明确的
  `permissions.allow` 列表——更可预测（对未列出的操作会静默拒绝，而
  不是去猜一个确认对话框），但需要操作者提前把所有允许的操作一一列
  出来。这不是当时被要求的东西；已记录在 DESIGN.md 的 Known
  limitations 里，作为将来自动 Enter 这个取舍如果被证明不可接受时可以
  转向的替代方案。
- **后果：** 一个在无人值守状态下、处于 `auto` 模式的确认提示，会被
  自动接受成当前无论默认/高亮的是哪个选项，而这并不保证是安全的
  选择——这是一个真实的、被有意接受的安全取舍，不是一个疏漏。
  `UNATTENDED_NUDGE_SEC="0"` 可以按部署单独关闭它，供将来需要重新
  审视这个取舍时使用。这项改动同时还暴露了（并修复了）两个只有在
  针对真实 `claude` 二进制和真实的 `systemctl restart` 做实机测试时
  才会发现的实现 bug：计时器从纪元 0 而不是循环启动时间开始计时
  （导致每次重启一个已经处于无人值守状态的会话时，都会立刻触发一次
  多余的提醒/刷新）——这一点和另外一个单独发现的 `KillMode` bug，都
  记录在 DESIGN.md 的 Known limitations 里。

## 2026-08-16 — 单一默认会话，而不是多会话模板化

- **背景：** 决定 `claude-guardian` 是否应该支持若干个并发受监督、各自
  具名的 `claude` 会话（例如通过一个 systemd 模板单元
  `claude-guardian@%i.service`）。
- **决策：** 只支持一个默认会话（`claude-code`），通过
  `/etc/claude-guardian/config.env` 配置。已经和用户确认过。
- **被否决：** 用 systemd 模板单元 + 按实例分配置目录来支持 N 个并发
  会话——真实的需求是"至少始终有一个可用"，而不是"始终有很多个可用"。
  多会话支持可以在真实需求出现之后再加（见 DESIGN.md 的"How to
  extend"）。
- **后果：** 更简单的单元文件、更简单的配置、更简单的 CLI（不需要在
  每个命令里都穿一个 `<name>` 参数）。如果操作者以后需要在同一台主机上
  同时运行不止一个 Claude 实例，再重新考虑这一点。

## 2026-08-16 — 两层监督：tmux + systemd，而不是 screen 或自定义守护进程

- **背景：** 需求是，一个 `claude` 实例既要能扛过一次主机重启，也要能
  扛过对 `claude` 进程本身的一次手动 Ctrl+C 杀掉，同时还要能通过 SSH
  被远程接管。
- **决策：** 两个相互独立的层——systemd（`Restart=always`）监督一个
  bash 循环，这个循环再负责保持一个 `tmux` 会话存活，并在 `claude`
  退出时重新生成那个窗格。见 DESIGN.md → Architecture。
- **被否决：**
  - **用 `screen` 代替 `tmux`** —— screen 没有等价于 tmux 的
    `#{pane_dead}` 那种可脚本化查询格式，无法拿来问"这个窗口里的进程
    是否还活着"；检测一个被 Ctrl+C 杀掉的进程，就得去轮询 `/proc` 或者
    解析 `screen -list`，两者都不够可靠。
  - **单层、纯 systemd 的设计**（`ExecStart=claude` 直接执行，
    `Restart=always`）——这样确实会在 `claude` 退出时重启它，但操作者
    会在每次重启时彻底丢失那个交互式终端/会话（没有回滚缓冲区，也没有
    办法"重新 attach"——systemd 单元本身不是可以直接 attach 的
    tty），也没有一套干净的远程接管方案。
  - **一个自定义的 Python/Go 守护进程** —— 相比直接调用 `systemd` +
    `tmux`（在每一台 Debian 目标主机上都已经现成存在）没有任何有意义
    的优势，代价却是多了一个构建/运行时依赖。
- **后果：** 这个工具同时依赖 `systemd`（假定已存在，不做检查）和
  `tmux`（会被检查，并由 preflight 自动安装）。安全地断开连接需要用
  tmux 的前缀键，而不是 Ctrl+C——这一点已作为一个使用上的坑点，记录在
  DESIGN.md 和 README.md 里。

## 2026-08-16 — 这个工具永远不会自己安装或自动认证 Claude Code CLI

- **背景：** 用户的明确指示：preflight 应该检查 `claude` 是否已安装、
  是否已登录，但绝不能尝试自己去安装 Claude Code。
- **决策：** `claude` 是否存在，是一个硬性失败的前提条件（只检查，不
  修复）；登录状态则是尽力而为的检查（查找已知的凭据文件位置），并且
  只会产生一个警告，从不阻止启动——`claude` 自己的交互式登录流程会在
  操作者第一次 attach 上去时自然而然地运行起来。
- **被否决：** 在 `claude` 缺失时，自动通过
  `npm i -g @anthropic-ai/claude-code` 或类似方式去安装它——按用户
  的要求，这明确超出了范围。
- **后果：** 在一台从未安装过 `claude` 的全新主机上，`install` 和
  `run` 都会带着一条可行动的错误信息大声失败，而不是替操作者做任何
  事情。
