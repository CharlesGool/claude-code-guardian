## 2026-09-12 — 会话以非特权账户运行，这正是 `--dangerously-skip-permissions` 得以成立的前提

- **背景：** 操作者要求受监督的会话以一个具备免密码 `sudo` 权限的普通账户运行，而不是 root，并搭配 `claude --dangerously-skip-permissions`。这两半其实是同一个请求：`claude` 在以 root 运行时会拒绝该参数并立即退出，所以只要会话还是 root 的，能用的最强"绝不停下来问"设置就只有 `--permission-mode auto`。这正是 2026-08-21 记录为真正的 v0.7.0 回归问题的那个拒绝行为——一个设置里要求 `bypassPermissions` 的 root 实例陷入崩溃循环。
- **决定：** 新增 `RUN_AS_USER`（全局，默认 `root`）。root 仍负责安装和监督；tmux 服务器、`claude` 以及监督循环则以该账户运行。`install` 会采纳 `$SUDO_USER`。出厂的 `CLAUDE_ARGS` 默认值变为 `--dangerously-skip-permissions --remote-control`，但 root 安装时例外，会得到 `--permission-mode auto --remote-control`。这种不可能的组合会被 `install`、`new` 和 `run` 在入口处直接拒绝。
- **为什么是全局而非按实例设置：** 每个实例共享同一个 tmux 服务器（2026-08-17），而一个 tmux 服务器只属于一个账户。按实例设置账户就需要一个账户一个服务器，这正是此前已被否决的设计。
- **为什么用 `passwd` 而不是 `$HOME`：** 在 `sudo` 下执行的管理命令拿到的是 root 的 `$HOME`。每一个派生路径——工作目录、`~/.claude/sessions`、`~/.claude/projects`——都会指向 root 的文件，而会话实际用的却是另一个账户的。同样的道理迫使 `claude` 的位置及其登录状态必须通过 `runuser` 来解析，而不是在调用者自己的 shell 里解析："claude 是否已登录？" 这个问题问的是某个账户的状态。
- **为什么默认仍保持 `root`：** 已有主机是通过重新运行 `install` 来升级的，而 `install` 从不改写已有配置文件。任何其他做法都会把一台在用主机的会话迁到另一个账户下，而会话对应的对话内容不会跟着一起过去。
- **为此付出的代价，是有意接受的：**
  - 更换账户后对话不会跟着走。`claude` 把对话记录保存在旧账户的 `~/.claude` 下，新账户读不到，而且记录目录是按工作目录命名的，往往在换账户的同时也会变。迁移是一套写好的手动流程，而不是工具自动做的事。
  - 工具现在会替用户回答 `claude` 首次运行时的信任提示（**No, exit** 是预选项，所以此前那种盲目按 Enter 的做法，会杀掉每一个新会话再把它重生进同一个死循环里）。替操作者选"是"是一个代为做出的决定；理由是 `$WORKDIR` 是他们为无人值守会话专门配置的目录。这个做法与该提示屏幕当前的措辞是绑定的——一旦措辞改变，这个重生循环就会重新出现，而日志只会写着 `claude exited`。
  - 出厂默认打开 `--dangerously-skip-permissions`，等于把该账户的全部权限交给了会话，包括在具备免密码 `sudo` 的账户上获得 root 权限。这是操作者自己要权衡的取舍，而 root 安全的替代方案只需一行配置。
- **动手过程中发现、并在同一版本中修复的问题：** 之前每一个 tmux 目标都是裸的会话名，而 tmux 会退化为前缀匹配。当 `claude-code` 和 `claude-code-work` 同时存在时，指向前者的命令会落到后者上——包括 `send-keys`，也就是说 `/remote-control` 和裸 Enter 会被发进属于另一个实例的对话里。目标现在都是精确匹配（会话目标用 `=name`，窗格和窗口目标用 `=name:`；均已在 tmux 3.2a 上验证）。这个问题在本版本之前就可能触发，但本版本让它变得更容易触发，因为 `install` 会在已有实例旁边再创建一个 `claude-code` 实例。
- **同样是实测中发现的：** socket 文件的存活时间会超过创建它的那个 tmux 服务器。切换账户后，遗留的、属主为 root 的 socket 导致每次创建会话都失败并报 `Permission denied`，而日志只会说 `claude` 已退出。`install` 现在会在没有服务器响应某个 socket 时移除它，而在仍有服务器响应时不去动它。

## 2026-08-23 — 弄清了"会话无法连接"这个故障的成因；这重新打开了 v0.7.0 的撤回决定

- **背景：** 操作者再次报告了这个由来已久的症状——某个会话在网页端显示 `(no content)`，桌面应用卡在 `connecting`，手机应用却宣称 `connected`，而通过 SSH attach 上去一切正常，唯独远程客户端都不行。此前认为这在主机侧是无法诊断的（"这里没有任何东西能检测出那种状态"）。这个认知是错的，而且弄清楚之后，工具反而暴露出比之前认为的更糟的问题。
- **动手之前，在现场实际观察到的情况：**
  - 两个互不相关的实例在一秒之内先后记录了 `remote control disconnected`，各自被发送了 `/remote-control`，三秒后监督进程记录下的 URL 与断线前的**完全相同**。真正的重新建立连接会生成一个新 id，所以这里其实什么都没有重建——但却记为成功。
  - 手动操作 TUI 解释了原因：在一个仍然自认为已连接的会话上执行 `/remote-control`，只会弹出一个信息性对话框（`Disconnect this session` / `Show QR code` / `Continue`），什么都不会重建。**监督进程唯一的修复动作，恰恰在最需要修复的那种状态下是无效的。**
  - 先在那个对话框里选 `Disconnect this session`，再执行 `/remote-control`，才会真正重新连接并生成新 id。这个修复机制本身是存在的。
  - 一次真正的重连会使 `bridgeSessionId` **发生变化**，所以它是一个有效的成功证明——但前提是把它当作一次"变化"来判断，而不是判断"非空"。
  - 这个故障会自我锁死：`claude` 只有在状态发生变化时才会重写它的会话文件，所以在一次失败的修复之后，那个陈旧的、非空的 id 会一直留在那里（被发现时已存在 6.2 小时），而每 5 秒一次的检查会永远读到"已连接"。日志因此保持干净，这就是这个问题此前看起来无法被检测出来的原因。
  - 在这个网络环境下，主机侧的 TCP 状态不能作为健康信号：出向流量会经过一个透明代理，所以即便对端已经断开，客户端 socket 也会因代理应答了 keepalive 而一直保持 ESTABLISHED 状态。两个互不相关的实例在同一秒内掉线，指向的是这条共享路径，而不是某个具体会话本身的问题。
- **决定：** 将此记录为*本工具自身*的一个已确认缺陷，并将修复它列为待办事项列表的最高优先级。诚实地划清责任：断线本身不是本工具的问题（一个未被监督的 `claude` 也会遇到），但一直保持断线状态就是本工具的问题——修复动作是无效的，而它的成功判据又依赖一个在修复动作什么都没做时根本不可能改变的值。
- **这与下面 2026-08-21 的撤回决定直接相关。** 那条撤回 v0.7.0/v0.8.0 的条目当时记录说，用来做决定的那个关键实验并未真正做过。现在这个实验做了，而结果指向相反的方向：v0.7.0 的两个核心机制——要求以 bridge id *发生变化*作为成功证明、以及先拆除再重建——恰恰就是今天的证据所显示需要的东西。**这条条目并不推翻那个决定**；那次撤回同时还移除了其他东西，而且操作者尚未确认新的 URL 能否在远程客户端上端到端地正常工作。它只是记录下：撤回决定所依赖的前提已不再成立，因此恢复那些被打包保存的引用需要重新评估，而不能就此当作已经了结。
- **被否决的方案：**
  - **认为 `claude-guardian url` 也有问题**——在同一次排查中曾被怀疑过，但已经排除：它读取的是实时的会话文件，并且正确跟踪到了新的 id。如果去修一个本没有问题的地方，只会掩盖真正有问题的那一处。
  - **把责任归咎于透明代理然后就此打住**——它很可能是最直接的触发因素，但工具本应能在自己无法控制的触发因素面前依然存活。一个无法完成修复的修复机制，无论是什么因素把连接打断的，都是一个缺陷。
  - **通过重启 `claude` 来恢复**——这确实有效，但相比那套对话框操作序列，这是一个大得多的手段，而且重启后的恢复是一套独立的机制，有自己的故障模式。一旦修复机制真正生效，就不再需要它。
- **已验证：** 上述每一项发现都是在一个实时运行的实例上直接观察到的——包括那个信息性对话框及其选项、`Disconnect` + `/remote-control` 的成功重连、发生变化的 `bridgeSessionId`，以及 `url` 能跟踪到新值。尚未验证的是：新生成的 URL 是否真的能在远程客户端上驱动该会话。这是操作者要做的测试，也是上面那项重新评估的前提条件。

## 2026-08-21 — 强制执行"至少一个会话"这条底线，并默认开启

- **背景：** 操作者问，如果一台主机上驻留的会话全部被关闭，重启后是否会自动恢复一个。答案是不会。下面 2026-08-16 的条目把这条最初的要求记录为"始终至少保有一个可用会话"，v0.1.0 的更新日志也写着这个工具"保持至少一个可远程连接的 Claude Code 会话存活"——但 v0.2.0 转向多实例模板化之后，就没有任何机制去强制执行这一点了。这是一种偶然形成的效果：`install` 会启用默认实例，systemd 会启动一切被启用的东西，而没有人把最后一个实例归档掉。`archive`（禁用+删除配置）和 `deactivate`（禁用）都可以在没有任何检查、没有任何警告的情况下把会话数量降为零；引出这个问题的那台主机，在 v0.7.0/v0.8.0 撤回之后正好处于这种状态，如果重启就会什么都起不来。
- **决定：** 两个机制，刻意分开设计。
  (A) `archive`/`deactivate` 在要移除的实例是开机时唯一会起来的那一个时，会发出警告——并且，除非带 `--yes`，还会询问确认。
  (B) 一个 `oneshot` 单元 `claude-guardian-floor.service`，每次开机运行一次 `ensure-floor`，在没有任何其他实例会起来时重新创建并启动默认实例。新增设置 `ENSURE_DEFAULT_INSTANCE`，**默认为 `1`**。
- **为什么默认开启：** 引出这次讨论的问题本身就是"这不是理应会自动恢复一个吗？"——如果默认关闭，那些不去读配置文件的人就会一直落空这个期望。一个存在的全部意义就是"始终有一个会话可达"的工具，不应该把这个保证做成需要主动开启的选项。退出方式是存在的，并且在三处文档中都有说明，这才是正确的顺序。
- **依据 `is-enabled` 计数，而不是依据配置文件：** `deactivate` 会保留配置文件，所以如果按 `$INSTANCES_DIR/*.env` 计数，会把那些永远不会启动的实例也算进去。这条底线要问的是真正重要的问题——systemd 实际会拉起多少个单元。
- **接受的后果：** 在 `ENSURE_DEFAULT_INSTANCE=1` 时，停用*最后一个*实例的效果会在下次开机时被撤销，这与 `deactivate` 本身"不会在开机时重启"的承诺相矛盾。这条底线保证优先，`deactivate` 现在会在动手之前明确把这一点说出来。真正想让主机以空闲状态开机的场景，应该设置 `ENSURE_DEFAULT_INSTANCE=0`；这和"停用所有实例"不是同一个操作，把两者混为一谈正是最初造成"静默归零"这种状态的原因。
- **被否决的方案：**
  - **只做警告（只有 A，没有 B）**——操作者的问题本来问的就是重启会发生什么，而对于一台已经处于零实例状态的主机来说，一个警告不能解决任何问题，而这台主机正好就处于这种状态。
  - **每次监督循环都持续运行的底线检查**——这会在一次刻意的 `archive` 操作之后几秒钟内就重新创建出一个实例，让 `archive` 变得没法用。每次开机执行一次，才是与"能挺过一次重启"这个承诺相匹配、又不会与操作者对着干的节奏。
  - **把这条底线并入实例模板单元里**——模板的单元只为已经启用的实例存在，所以在恰恰需要修复的那种状态下，它们一个都不会运行。这必须是它自己独立的单元。
  - **在底线机制内部使用 `systemctl enable --now`**——在开机事务内部去等待另一个单元的启动任务完成，存在死锁风险；用 `enable` + `start --no-block` 能达到同样的效果而不会阻塞。
  - **复用版本号 `v0.7.0`**——那个标签和 `v0.8.0` 都曾被推送又被删除。任何拉取过其中之一的人，再次拉取时会在同一个名字下得到不同的代码，这正是发布规范禁止移动已发布标签的原因。这次发布用的是 `v0.9.0`；`v0.7.0` 和 `v0.8.0` 保持作废状态。
- **已验证：** shellcheck 检查通过；在一个隔离的沙箱路径树中，针对模拟的 `systemctl`/`claude` 跑了一套 48 个用例的测试（底线数量为零/一/二/所有实例都被停用/主动关闭该功能的情况；开启和关闭该设置两种情况下，在非 tty 和在 pty 下，`archive` 和 `deactivate` 时警告的出现与否；`--yes` 的处理；install/uninstall/purge 对单元的接线；对 `list`/`archives`/usage 的回归测试）。同一套测试跑在 v0.6.2 基线上会有 48 项中的 27 项失败，说明它确实能检测出这项工作缺失的情况，而不只是恰好与结果一致——这正是下面 v0.6.1 那个缺陷条目里学到的教训。之后又在维护者的真实主机上、用真正的 systemd 做了实测：`install` 写入并启用了底线单元；在没有 `--yes` 的情况下停用唯一的实例被拒绝，加上 `--yes` 则给出警告；在零实例状态下启动底线单元恢复了该实例（真实的 `claude` 进程、tmux 会话正常，且没有出现开机死锁）；再次启动它会记录 `already enabled — nothing to do`，且没有创建出第二个会话。
- **未做实测验证的部分：** 实例配置文件完全缺失的那条分支（对应 `archive` 路径）——沙箱测试覆盖了这一点，但在真实主机上 `archive` 被一个权限分类器拦住了，且没有想办法绕过去。也没有做过真正的重启测试；底线单元是通过直接启动它来验证的，这与 systemd 在开机时执行的是同一条代码路径。

## 2026-08-21 — 撤回 v0.7.0 和 v0.8.0；代码基线回到 v0.6.2

- **背景：** 四个受监督的实例，以及另外一个工具并未在监督的普通 `claude`，在闲置一段时间后全部从 claude.ai 变得无法连接（"Can't reach your computer"）。监督进程的日志在第一次记录到掉线之前，有长达十一小时的窗口是干净的，这正是本项目自 v0.6.0 以来一直在追查的那种故障模式。
- **决定：** 维护者判断 v0.7.0 中 Remote Control 的重构是根源所在，因而将其撤回。已安装的二进制文件回滚到 v0.6.2；`v0.7.0` 和 `v0.8.0` 这两个标签在本地和远程都被删除，`v0.7.0` 的 Release 对象也被删除，两份快照目录都被移除，`main` 分支被强制重置到 `v0.6.2`。此后的所有工作都从 v0.6.2 这个基线重新开始。
- **判断依据（维护者的判断）：** 掉线现象是在 v0.7.0 发布之后开始出现的，而在 v0.6.2 上没有观察到。
- **针对这个判断记录下的反证，以免日后凭记忆重新争论：** (1) 同样的掉线发生在一个运行在 tmux 之外的普通 `claude` 进程上，而那个时刻并不存在任何受监督的实例，本工具的任何版本都不可能导致一个它根本没在监督的进程掉线；(2) v0.7.0 自己的更新日志把"一个实例可能在日志干净的情况下无限期地处于无法连接的状态"列为它*修复*的一个缺陷——那正是 v0.6.2 的行为，所以这次回滚等于把它又恢复了回来；(3) v0.7.0 真正的回归问题，是从 `CLAUDE_ARGS` 里去掉了 `--permission-mode auto`，这会让设置中要求 `bypassPermissions` 的 root 实例陷入崩溃循环，而 v0.8.0 早已针对性地修复了这一点。这个决定是在这三点都摆在桌面上的情况下做出的。
- **撤回所付出的代价：** `reconnect` 命令、一套隔离的 23 个用例的 Remote Control 测试、`REMOTE_CONTROL_MAX_BRIDGE_AGE_SEC`（这是唯一能从上游静默失效的 bridge 中自动恢复的机制），以及 `BACKLOG.md`。在有东西能替代它们之前，对付一个无法连接的会话，唯一的办法就是 attach 上去手动输入 `/remote-control`。
- **另有发现，且这一点不受这次决定影响：** bridge id 在重启后依然存活。一个被杀掉、又用 `claude --resume` 恢复的实例，会重新连上*同一个* `bridgeSessionId`，所以对应的 claude.ai URL 不会变（已在四个实例上验证）。因此这个 id 不能被当作"有东西正在正常流动"的证明，而重启之后 URL 不变，也不是什么异常症状。
- **尚未了结、这也是本条目存在的原因：** 在做出删除决定时，那个用来做最终判断的关键实验并没有真正做过——让某个实例闲置一整晚，看看 v0.6.2 是否也会掉线。如果会，那么根源就在 Remote Control 这条连接链路本身，而不在这个工具，那么被撤回的那些工作就值得找回来；在删除之前已经把每一个被删掉的引用都完整打包保存了下来，具体位置记在维护者的本地笔记里。如果不会掉线，那么上面的判断就得到了确认，应该去查的地方就是 v0.7.0 的那份 diff。

## 2026-08-17 — 每个监督周期都检查连接状态，并且默认不再自动应答对话框

- **背景：** v0.4.0 带着三个实例上线还不到一小时，操作者就报告了"怎么其他两个会话都disconnected了"。两个实例确实都真的断开了（`bridgeSessionId: null`），而且除此之外一切正常——都还活着、都在对话过程中，只是从 claude.ai 那边连不上而已。其实什么都没坏：监督进程每 `REMOTE_CONTROL_REFRESH_SEC`（1200 秒）检查一次，而其中一个实例就在我们正盯着看的时候，在下一次检查时自愈了。**这本身就是问题所在。** 同一次排查还揭示了另一半问题：那个实例的日志里有三行 `sending Enter`——这个无人值守时的"轻推"功能，替操作者应答了他们已经从 claude.ai 打开、但还没来得及自己回答的确认对话框。
- **决定（关于连接）：** 检查改为每个监督周期都执行一次（`REMOTE_CONTROL_CHECK_SEC`，默认 5 秒 = `CHECK_INTERVAL_SEC`），而重连动作则用它自己独立的计时器做限速（`REMOTE_CONTROL_RECONNECT_BACKOFF_SEC`，默认 60 秒）。`REMOTE_CONTROL_REFRESH_SEC` 被移除，如果某个配置里仍然设置了它，会在启动时给出警告。
- **为什么这样改：** 1200 秒这个数字是从 v0.2.0 沿用下来的，那时它的含义是"每隔多久重新发送一次 `/remote-control` 以保持连接存活"。v0.3.0 证明了这个假设是错的，把检查改成了被动方式，却保留了这个数字——于是一个原本按"按键间隔"设定的数值，悄悄变成了"一个实例最长可以无法连接多久"。读一个文件不花什么代价，也不会往里输入任何东西；从来就没有理由把它做得这么慢。把两个计时器分开正是让这样做变得安全的关键：只有重连动作才会真正触碰会话，所以也只有重连动作才需要限速退避。极端情况（根本不存在可用的会话文件，因而永远无法确认是否成功）保留了一个慢得多的内部 1200 秒重试，否则它会一直不停地往那个会话里输入 `/remote-control`。
- **决定（关于轻推功能）：** `UNATTENDED_NUDGE_SEC` 默认改为 `0`——除非操作者明确打开这个功能，否则监督进程不会去应答确认对话框。
- **为什么这样改：** v0.4.0 曾假设"没有 tmux 客户端连接 + 停在某个对话框上超过设定时长"是判断"已被放弃"的一个可靠代理指标。实际生产环境表明这个假设并不成立：Remote Control 并不是一个 tmux 客户端，所以一个正在手机上查看对话框的操作者，和一个被彻底放弃的会话是没法区分的，而按 Enter 会直接确认当前高亮的那个选项。被否决的替代方案包括：调大这个时间间隔（只是缩小了出问题的窗口，故障模式本身还在，而且拖慢了真正需要恢复时的响应速度）；只在 Remote Control 处于*已连接*状态时才把它当作"有人能来应答"、并只在断开状态下才去轻推（这依然是一种猜测——一个已连接的会话同样可能被彻底放弃，而且在这次事故里两个实例本来就都是断开状态，这样改根本不会有任何区别）；保持功能开启但把文档写得更详细（v0.4.0 已经写过文档，结果还是让写文档的人自己都感到意外）。这个功能本身被保留下来，带着它那个只在 `waiting` 状态下才生效的限制，留给那些希望实例能自己摆脱卡住状态的操作者——只是它不再是默认行为。
- **后果：** 一个被放弃、卡在某个对话框上的实例，现在会一直卡在那里，直到有人来应答它。这正是刻意接受的取舍：监督进程的职责是让会话保持*可连接*，而不是替会话内部做决定。

## 2026-08-17 — 让对话在重启之后能够继续，而不是重新开始一个空的对话

- **背景：** 操作者在 v0.3.0 已经运行了一段时间之后的反馈是："重启后恢复的也没有记录啊，所以没什么意义"——重启之后实例确实恢复了，但每一个都是从一段空白对话开始的，所以真正保住的是*进程*本身，而不是*工作内容*。这原本被记录为 v0.3.0 的一个已知问题；实际生产使用让它成了两个已知问题中更重要的那一个。
- **实际发生的情况是：** `respawn-pane` 会复用窗格原本的命令行，所以一个崩溃的 `claude` 会以同一个 `--session-id` 重新启动——这条路径原本一直没问题。重启则不一样：它会把 tmux 服务器一起带走，所以走的是 `create_session` 这条路径，而它此前是无条件地用 `uuidgen` 生成一个全新的 id。这一点在操作者的主机上得到了确认：重启前的对话记录文件本身完好无损（4.6 MB，最后一次写入是在重启前七分钟），只是变成了孤儿文件，没人再引用它。
- **决定：** `create_session` 现在会优先使用该实例自己上一次的 `claude_session_id`——这个值已经保存在状态里，供 `archive`/`resume` 使用——并以 `claude --resume <id>` 启动，前提是该对话对应的记录文件在 `$CLAUDE_PROJECTS_DIR` 下依然存在。优先级顺序为：显式指定的 `RESUME_SESSION_ID`（来自 `resume <archive-id>`），其次是该实例自己此前的对话，最后才是生成一个新 id。设置 `RESUME_AFTER_RESTART=0` 可以恢复旧的行为。
- **被否决——不检查记录文件，无条件地执行 resume。** 这样能少依赖一层内部实现细节，但代价是把一个 `claude` 可能根本没见过的 id 交给它，而且这种失败是"先静默、后致命"的：`claude` 会立即退出，监督进程会在每个 `CHECK_INTERVAL_SEC` 重新构造出同一条会失败的命令，这个实例就再也起不来了。而先检查一下，只需要多付出一次 `[ -r ]` 的成本。
- **被否决——使用 `claude --continue`（恢复当前工作目录下最近的一次对话）。** 这样完全不依赖对话记录文件的路径，但"当前工作目录下最近的一次"并不等同于"属于这个实例自己的那次"：两个共享同一个 `WORKDIR` 的实例，或者操作者手动在那里跑过的任意一次对话，都可能被错误的那个实例接管。实例的身份识别必须依赖本工具自己保存的状态。
- **被否决——resume 时加上 `--fork-session`。** 这样能让每次开机的历史都保持独立、便于查阅，但代价正是这个需求本身想要的东西：跨越多次重启的一段连续对话。
- **接受的代价：** 对话记录文件的路径（`$CLAUDE_PROJECTS_DIR/<工作目录中所有非字母数字字符都替换为 `-` 之后的结果>/<id>.jsonl`）是 Claude Code 的一个内部实现细节，已针对 2.1.202 版本验证过，和 `bridgeSessionId` 属于同一类风险。缓解方式也一样：这个路径是可配置的，并且如果没能命中，会退化为开启一个新对话，而不是直接失败。需要留意的失败模式是无声的——如果这个约定发生变化，每次重启就会悄无声息地又变回从头开始。
- **另外接受的情况：** `claude` 因为某种其他原因拒绝了这次 `--resume`。`create_session` 会在启动几秒钟之后检查一次该会话是否已经死掉——或者根本没能成功建立，因为 `remain-on-exit` 只在 `new-session` 返回之后才会被设置，所以一次很快的退出会把整个会话一起带走——如果是这样，就以一个新的对话重试。这后半部分是在隔离测试中发现的，而它正是这项检查存在的意义所要防止的那个"无限循环"缺陷。
- **对操作者而言的后果：** 在实测中观察到、值得知晓的一点是——由于 `claude` 的会话 id 没有变化，实例对应的 `claude.ai/code/...` URL 在测试中也随之在重启后保持不变。这是 Remote Control 绑定会话的方式所带来的一个副作用，而不是一个承诺；仍然应该用 `claude-guardian url <name>` 去获取 URL。

## 2026-08-17 — 只轻推那些真正卡在对话框上的会话，而不是那些看起来无人值守、实则未必如此的会话

- **背景：** v0.3.0 的第二个已知问题。`UNATTENDED_NUDGE_SEC` 会向任何没有 tmux 客户端连接的实例发送两次 Enter，每 300 秒一次。而 Remote Control 并不是一个 tmux 客户端，所以一个操作者正在从 claude.ai 上操作的会话也会被算作符合条件——这在空闲的提示符下无关紧要，但却有可能替操作者应答一个确认对话框。
- **决定：** 把这次轻推动作的触发条件，改为依据 Claude Code 自己在 `$CLAUDE_SESSIONS_DIR/<pid>.json` 中记录的 `status` 字段。已在 2.1.202 版本上实测观察到三种取值：`busy`（正在处理某一轮对话）、`idle`（提示符为空）、`waiting`（卡在某个确认对话框上）。只有 `waiting` 状态才会被输入内容，并且只在 `statusUpdatedAt` 显示该对话框已经无人应答超过 `UNATTENDED_NUDGE_SEC` 之后才会触发——也就是说倒计时是从对话框出现的那一刻开始算的，而不是从监督进程碰巧看一眼的那一刻开始算。这也让这个轻推功能变得更加有用：它只会在它当初设计要处理的那一种状态下触发，而不是靠一个定时器、大多数时候打在根本没什么可清除的会话上。
- **被否决——改为依据 `updatedAt`（最后活动时间）来判断。** 这是最先尝试的方案，一开始看起来是对的，直到拿一个真实会话去检验：维护者自己的一个实例已经处于处理中状态长达二十分钟，而它的 `updatedAt` 却依然是二十分钟前的旧值，因为这个字段追踪的是状态*切换*，而不是持续进行中的工作。依据它来触发轻推，恰恰会把 Enter 输入到这项改动本来是为了保护的那个会话里。
- **被否决——只要 Remote Control 处于已连接状态就跳过轻推。** 用 v0.3.0 已有的信息实现起来很简单，但由于每个实例默认都开启了 `--remote-control`，这样做会让轻推功能在所有地方都失效，而不是把它收窄到真正需要的范围。
- **接受的代价：** 一个在 claude.ai 上打开了某个对话框、打算稍后回答、却把它晾在那里超过 `UNATTENDED_NUDGE_SEC` 时长的真人操作者，和一个已经被放弃的会话是无法区分的，因此依然会被替他应答。要调整就调大这个时间间隔这个参数。在不存在可用的会话文件的情况下，仍然保留 v0.2.0 那套按墙钟时间判断的行为作为兜底。

## 2026-08-17 — `MAX_SESSIONS` 默认值改为 0（不限制）

- **背景：** 操作者遇到了 `MAX_SESSIONS=3`，并把它理解成了这个工具本身的限制——"对话为什么有3个限制，我实测可以开很多啊?"——这是一种错误的心智模型：这个上限从来只作用于受 guardian 监督的实例，从未作用于 Claude Code 本身。
- **决定：** 默认值改为 `MAX_SESSIONS="0"`，含义是不限制，同时仍然把这个上限选项保留给想要设置它的人使用。`0` 这个取值必须被明确赋予这层含义；在此之前，`0` 会导致每一个实例都被拒绝，因为原来的检查逻辑就是简单的 `count >= MAX_SESSIONS`。
- **被否决——彻底移除这个设置项。** 这背后的成本考量是真实存在的（每个实例都是一个独立的 `claude` 进程，会占用独立的 token 预算）；真正有问题的地方在于默认就给所有人强加了一个具体数字。
- **后果：** 已有的安装环境会保留它们 `config.env` 里原本已有的值——`install` 是刻意从不覆盖它的——所以这次改动只影响全新安装得到的默认值。

## 2026-08-17 — 从 claude 自身的会话文件读取 Remote Control 状态，而不是抓取终端画面

- **背景：** 运维方报告了生产环境中的两个症状：会话在闲置一段时间后在 claude.ai 上显示"已断开"，以及每次开机后都会多出一个对话。对这两个症状的调查揭出了四个独立的问题，其中三个出在本工具身上。
- **实际问题所在：**
  1. **v0.2.0 的 keepalive 什么也没做。** 它每隔 `REMOTE_CONTROL_REFRESH_SEC` 就重新执行一次 `/remote-control`，以为这样能刷新连接。经对照真实二进制核实：当 Remote Control *已经*处于开启状态时，`/remote-control` 只会打开一个信息对话框（"Disconnect this session" / "Show QR code" / "Continue"），不会重新建立任何连接。所以当连接真正断开时，没有任何东西去修复它——这正是被报告的症状。
  2. **URL 抓取可能捕获到别人的 URL。** 它对整个可见窗格用 `https://claude.ai/code/session_...` 做 grep 并取最后一个匹配。实测抓到过：`claude-code` 实例的屏幕上显示了另一个实例的 URL（运维方当时正在那里调试），刷新逻辑把*那个* URL 写进了 `claude-code` 的状态，导致 `claude-guardian url claude-code` 返回的是另一段对话的链接。任何恰好出现在屏幕上的会话 URL——一条 commit 附言、某个命令的输出——都可能引发这个问题。
  3. **"无人值守"这个判断标准本身就用错了地方。** Remote Control 不是 tmux 客户端，所以一个正被人从 claude.ai 端主动操作的实例，看起来会像是"无人值守"，于是周期性注入的 `/remote-control` 会作为一次用户输入，直接落进*那段正在进行的对话*里。
  4. 不是工具的 bug：v0.2.0 验证时遗留的一个 `test` 实例仍处于启用状态，导致开机时启动了两个实例。已归档处理。
- **决定：** 停止从终端画面推断 Remote Control 状态。Claude Code 会为每个运行中的会话写入 `$CLAUDE_SESSIONS_DIR/<pid>.json`，其中的 `bridgeSessionId` 字段在连接期间保存 Remote Control 会话 id，断开后变为 `null`；由于一个实例的 `claude` 就是其 tmux 窗格的命令进程，`#{pane_pid}` 可以直接对应到该文件名。读取该文件即可回答"是否仍然连接？"和"URL 是什么？"这两个问题。`REMOTE_CONTROL_REFRESH_SEC` 的含义也随之改变：现在它表示该检查多久执行一次，只有当检查结果显示连接确实已断开时，才会发送按键。对于健康的实例，监督进程现在完全不会输入任何内容。
- **驳回 —— 继续抓屏，但把正则锚定到 `/remote-control` 的输出上。** 这能修好"抓到错误 URL"的问题（事实上也保留下来，作为 Claude Code 不写会话文件时的兜底方案），但无法解决真正的问题：它仍然需要向会话里输入内容才能获取信息，因此在不打扰一段可能有真人参与的对话的前提下，无法区分"已连接"和"已断开"。
- **驳回 —— 通过状态栏中的 `/rc` 指示符检测连接状态。** 那个指示符来自运维方自己的 `claude-hud` 状态栏插件，而不是 Claude Code 本身，所以这个方案只能在一台机器上生效。
- **驳回 —— 每次检查都无条件重新连接。** 简单且始终最新，但每次重连都会铸造一个新的 `claude.ai/code/...` URL（实测核实：在一段未受其他干扰的会话上，仅一次断开/连接循环后 id 就发生了变化），这样每 20 分钟就会无谓地更换一次 URL，没有任何好处。只在真正断开时才重新连接。
- **接受的代价：** `bridgeSessionId` 是 Claude Code 的内部实现细节，并非承诺稳定的接口，此结论是针对 2.1.202 版本核实的。通过三种方式缓解：路径可配置（`CLAUDE_SESSIONS_DIR`）；读取结果会与该实例自身的 `pid` 及所追踪的 `claude_session_id` 交叉核对，防止被重用的 PID 返回别人的会话；文件不可读时会降级回 v0.2.0 的抓屏方案，而不是直接失败。
- **对运维方的影响：** 一次重新连接会改变该实例的 URL，所以这个 URL 应该是按需获取的东西（`claude-guardian url <name>`），而不该被收藏。已在 README 和 DESIGN 中记录说明。

## 2026-08-17 — 推翻"单一默认会话"（2026-08-16）：加入具名的并发多实例支持

- **背景：** 运维方的实际工作流演变为需要同时拥有若干个独立、并发受监督的 `claude` 对话（例如每个项目一个），每个都可以单独远程控制，并且能够暂停（"取消激活"）或永久归档某一个而不影响其他的——这些都是单实例设计做不到的。在动手实现之前，先通过实测核实了一个 claude.ai 账号*确实可以*同时承载多个并发的 `--remote-control` 会话（运维方此前已经在手动这样操作了）——这正是下方 2026-08-16 决策中留下的唯一悬而未决的技术疑点（"如果运维方之后需要同时运行多个 Claude 实例，再重新审视此决定"）。
- **决定：** 把 systemd 单元改造成模板（`claude-guardian@<name>.service`），做法与当时 DESIGN.md "How to extend" 一节中所勾勒的方案一致。一个 tmux server（一个 `TMUX_SOCKET`），多个具名会话——tmux 本身就原生支持这种用法，所以不需要为每个实例单独开一个 socket。各实例专属配置存放于 `/etc/claude-guardian/instances/<name>.env`（仅覆盖 `WORKDIR`/`CLAUDE_ARGS`/`CLAUDE_BIN`）；`TMUX_SOCKET`、`CHECK_INTERVAL_SEC`、`REQUIRED_APT_PKGS`、`UNATTENDED_NUDGE_SEC`、`REMOTE_CONTROL_REFRESH_SEC`，以及新增的 `MAX_SESSIONS`，仍然保持为全局的、整机共享的配置项——为这些配置项添加逐实例覆盖并非真实需求，这样做只会让配置面翻倍，却换不来任何被要求过的收益。
- **本次推翻中新增的能力：**
  - `new` / `activate` / `deactivate`：分别对应创建、恢复监督、暂停监督但不杀掉会话。`deactivate` 被刻意设计成与 `archive` 相区分——运维方要求的是"取消激活"（暂停）和"归档"两种分别代表非破坏性与破坏性的独立操作。
  - `archive` / `resume` / `archives` / `rm-archive`：运维方确认归档应当在保存状态后**杀掉**存活的 claude 进程（而不只是取消激活并让它继续在后台运行）——详见下方"归档会杀掉进程"这条子决定。
  - 每个实例在创建时现在都会带上一个 `claude --session-id <uuid>`（通过 `uuidgen` 生成，因此在 `REQUIRED_APT_PKGS` 中加入了 `uuid-runtime`），而不再让这个 id 隐式存在，目的正是让 `archive` 能够记录下哪个磁盘上的对话（`~/.claude/projects/<escaped-cwd>/<uuid>.jsonl`）属于哪个实例，`resume` 也能把同一个 id 交还给 `claude --resume <uuid>`。已直接核实：`claude --help` 暴露了 `--session-id`、`--resume`、`--fork-session` 这几个参数；对话记录确实存在于该路径下（已在本机自己的 `~/.claude/projects/-root/*.jsonl` 上核实）。
  - claude.ai 的远程控制 URL（`https://claude.ai/code/session_...`）现在会在每个实例启动后立即从 tmux 窗格中抓取（并在每次无人值守的 `/remote-control` 刷新时重新抓取），保存到逐实例状态中，这样 `claude-guardian url <name>` / `list` 就能打印出来，完全不需要人去 attach——这正是运维方明确提出的目标（"以后都不需要终端"）。已实测核实：`/remote-control` 运行后，`tmux capture-pane -p` 的输出中确实立即出现了 `https://claude.ai/code/session_...` 这段文字。
- **子决定 —— 归档会杀掉进程，而不只是取消激活：** 已与运维方明确确认（直接询问：仅取消激活 vs. 先保存再杀掉两种方案）。理由：一个"已归档"的实例应当释放它占用的 tmux 窗格和进程资源，而不应该永远暂停在那里、还占着与 `MAX_SESSIONS` 相关的资源限额；在杀掉进程之前，会把回滚缓冲区（scrollback）和 `claude_session_id` 保存到 `/var/lib/claude-guardian/archive/`，专门确保对话内容不会有任何丢失。
- **驳回：**
  - **保持单实例，让运维方自己手动运行第二份不相关的工具副本** —— 这违背了"守护"这件事本身的意义：第二份副本将得不到任何监督、不会自动重启、没有无人值守时的 keepalive，也没有统一的 `list`/`archive` 管理方式。
  - **每个实例单独一个 `TMUX_SOCKET`**（每个实例一个 tmux server）—— tmux 本身已经能在一个 server 上多路复用多个会话；每个实例再开一个 server 只会增加运维开销（需要追踪 N 个 socket、维持 N 个 server 存活），却换不来任何新能力。
  - **提供一个 REST/HTTP 控制 API 用于生命周期管理** —— 运维方提出的需求是基于 CLI/remote-control 的（"不需要终端"指的是不需要 SSH 进去，而不是要替换掉 CLI 本身，CLI 仍然是通过远程 `claude` 会话调用本工具自己的命令来驱动的）；引入一个面向网络的控制平面，会给一个单人运维、单主机的工具带来一次巨大且未被要求过的攻击面扩张。
- **后果：** 所有以前不带实例参数的、已有文档记录的命令（`attach`、`logs`、`start`、`stop`、`restart`、`status`）在不带参数时依然可用，默认指向 `claude-code` 这个实例，这样一套已有的 v0.1.0 部署在升级后，运维方熟悉的手感命令仍然照常好用。在已有 v0.1.0 主机上执行 `install`，会禁用/移除旧的非模板化单元，并在新模板下（`claude-guardian@claude-code.service`）重新启用同一个 tmux 会话——由于新旧两个单元都设置了 `KillMode=process`，这个操作永远只会停掉监督*循环*本身，绝不会停掉 tmux server 或其中的 `claude` 进程，因此进行中的对话能够在升级过程中安然无恙。`purge` 的影响范围从"一个会话"扩大到了"每一个存活实例"——它现在会打印出存活实例的数量，并要求交互式确认（或传入 `--yes`）才会继续，而且刻意不去动 `/var/lib/claude-guardian/archive/`（归档必须通过 `rm-archive` 显式移除），这样一次完整的清空操作就永远不会悄无声息地销毁一段已归档的对话。

## 2026-08-16 — `install` 在 claude 未登录时硬性拒绝；登录检查改为使用 `claude auth status`

- **背景：** 用户要求增加一个真正能在 Claude Code 尚未登录时阻止安装的登录检查（此前，缺少登录状态在 `install` 和 `run` 时都只会产生一条警告）。
- **决定：**

  - `preflight_enforce`（`run` 和 `install` 共用）保持其原有的非阻塞行为不变，只是现在使用更准确的检查方式。
- **驳回：** 把这个硬性拦截合并进 `preflight_enforce` 本身——这样做还会导致 `run`/正在运行的 systemd 服务，在安装成功之后一旦丢失登录状态就直接硬性失败——这超出了本次实际被要求的范围（本次要求specifically针对的是*安装*这一步），并且会把一个本可恢复的状况（通过 `attach` 重新登录即可）变成一个已经在正常运行的部署陷入"重启即失败"的死循环。
- **后果：** 现在 `install` 要求事先已经完成过 `claude auth login`（或任何其他方式的登录）——先部署好守护进程、之后再通过 `attach` 交互式登录的做法，不再可行；登录必须先于安装完成。

## 2026-08-16 — 首次运行和无人值守 nudge 时发送两次回车（而非一次）；新增 `purge` 命令

  - `create_session` 现在会在启动 `claude` 之后立即发送两次回车（间隔一秒），而不再仅仅依赖无人值守 nudge 的计时器最终清掉首次运行画面。

- **驳回：** 在决定要发送多少次回车之前，先去检测当前具体显示的是哪种画面（信任对话框 vs. onboarding vs. 已经处于正常提示符）——考虑到多发一次无害的回车已经能达到同样的效果，不值得为此增加额外的脆弱性。同时也驳回了直接改变 `uninstall` 现有行为，而不是新增一个独立的 `purge` 命令——保留会话不动的安全默认行为是一个已经过测试、值得刻意保留的属性，应当与彻底清空区分开。
- **后果：** `purge` 会无条件杀掉任何存活的 claude 会话——已在文档中清楚说明这正是它与 `uninstall` 的区别所在。没有针对本机真实的 systemd 单元进行端到端测试（那样做会拆毁正在生产环境运行的部署）；改为通过代码审查，以及复用已经经过测试的 `cmd_uninstall` 模式，再加上对本工具自身拥有的路径（`/etc/claude-guardian`、`/run/claude-guardian`、已安装的二进制文件）执行简单直接的 `rm -rf` 来完成验证。

## 2026-08-16 — 将 CLAUDE_BIN 解析为绝对路径，不信任 systemd 自身的 PATH

- **背景：** 在第二台主机上进行的一次全新 `install` 顺利完成，但服务立即进入了 `failed` 状态。`preflight_enforce` 中的 `command -v "$CLAUDE_BIN"` 检查，在 `install` 过程中交互式运行时一切正常，但当 systemd 自己运行 `claude-guardian run` 时却失败了——systemd 的默认 PATH（`/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin`）不包含 `~/.local/bin`，而这正是典型的 npm/pip 用户级安装中 `claude` 所在的位置。本机自己的部署恰好因为在 `/usr/bin/claude` 处还有第二份 `claude`（一个诱饵）而掩盖了同样的潜在 bug，所以这个问题此前一直没有在本机暴露出来。
- **决定：** 分两部分修复，均已通过真实的功能测试（而非仅靠代码审查）核实：（1）`write_default_config` 现在在安装时通过 `command -v` 解析 `CLAUDE_BIN`——使用安装程序自身、拥有完整 PATH 的交互式 shell 环境——并把解析出的绝对路径固化进 `/etc/claude-guardian/config.env`，这样全新安装就永远不会遇到这个问题。（2）`preflight_enforce`/`preflight_report` 在普通查找失败时，会回退到通过 `bash -ic "command -v claude"` 来解析 `claude`，这样已经安装过、配置里仍写着裸 `"claude"` 默认值的主机，也能在下一次 `run`/`check` 时自我修复，而不需要手动去改配置文件。
- **驳回：** 用 `bash -lc`（login，非交互式）作为回退机制——经测试确认这**不**可行：Debian 默认的 `~/.bashrc` 开头就是 `[ -z "$PS1" ] && return`，这一行对任何非交互式调用（包括 `bash -l`）都会触发，于是脚本在读到 `PATH=` 那一行之前就已经返回了。`bash -ic`（交互式）才是真正能让 bash 设置 `$PS1` 并继续执行 `~/.bashrc` 剩余内容的方式——这是经过实测确认的、导致本方案最初版本行不通的真实原因，而不是一个假设性的猜测。
- **后果：** `bash -ic` 会在非 tty 环境下向 stderr 打印一些任务控制/终端相关的警告（无害，会被丢弃——已核实这些噪音不会混入被捕获的 stdout 值中）。每次 `preflight_enforce` 调用，在快速路径失败时都可能额外派生出一个交互式 shell——这只会发生在 `CLAUDE_BIN` 尚不可直接解析的情况下，代价可以忽略不计，而且只出现在失败路径上。

## 2026-08-16 — 始终保持可远程控制：`--remote-control` 设为默认值，无人值守自动回车被接受为一项明确的权衡取舍

- **背景：** 用户报告最初的设计还不足以做到"始终可远程控制"——具体要求了 `claude --permission-mode auto --remote-control`、一个用于清除卡住确认提示的自动回车机制，以及一个针对 Claude Code 在长时间无活动后变得不可控这一问题的修复方案。
- **决定：**
  - `CLAUDE_ARGS` 现在默认使用 `--permission-mode auto --remote-control`。已实测核实 `--remote-control` 会打印出一个可从网页/手机端控制的 `claude.ai/code/...` URL，独立于 SSH 之外——这现在是主要的远程控制路径，SSH + `tmux attach` 作为后备方案（DESIGN.md 的 Goals/Architecture 部分已相应更新）。
  - 在 `supervise_loop` 中新增了一个仅在无人值守时生效的 keepalive：当 `tmux list-clients` 显示无人 attach 时，在经过 `UNATTENDED_NUDGE_SEC`（默认 300 秒）后发送一次单独的回车，用来清除 `auto` 模式回退产生的任何确认提示，并在经过 `REMOTE_CONTROL_REFRESH_SEC`（默认 1200 秒）后重新执行一次 `/remote-control`，赶在 Anthropic 文档记载的约 30 分钟"could not reach the Remote Control server"阈值之前刷新连接。信息来源：`claude --help`（本地核实的参数存在性）、Anthropic 的 `remote-control.md` 和 `permission-modes.md` 文档（30 分钟阈值、auto 模式的回退行为——来自资料调研，并未独立端到端复现）。
  - 这个自动回车机制在首次部署时，**被 Claude Code 自身的 auto 模式分类器当场标记**（"在未经用户明确授权的情况下，绕过了人工介入这一安全兜底机制"）——它会接受当前高亮/默认的那个选项，而不知道那对于当前这个具体提示来说是否是安全的选择。已将这一权衡取舍明确呈现给用户（自动回车 vs. 更可预测、但需要更多前期配置的 `--permission-mode dontAsk` + `permissions.allow` 方案）；用户确认按照最初的要求，继续采用自动回车方案。
- **驳回：** `--permission-mode dontAsk` 配合显式的 `permissions.allow` 列表——更可预测（对未列出的操作静默拒绝，而不是去猜测某个确认对话框该怎么点），但要求运维方事先枚举出所有允许的操作。这不是本次被要求的方案；已在 DESIGN.md 的 Known limitations 中记录为一个备选方案，供日后如果发现自动回车这个权衡取舍在实践中无法接受时使用。
- **后果：** 在无人值守状态下，一个处于 `auto` 模式的确认提示会被自动接受为当前默认/高亮的那个选项，而这并不保证是安全的选择——这是一项真实的、被主动接受的安全权衡取舍，而不是疏漏。`UNATTENDED_NUDGE_SEC="0"` 可以按部署逐一禁用该机制，供日后需要重新审视这一权衡取舍时使用。在针对真实 `claude` 二进制和真实 `systemctl restart` 进行实测的过程中，还额外发现（并修复）了两个实现层面的 bug：计时器从纪元 0（epoch 0）而不是循环启动时刻开始计时（导致每次重启一个本已无人值守的会话时，都会立即触发一次多余的 nudge/刷新）——另一个是单独发现的 `KillMode` bug，两者详见 DESIGN.md 的 Known limitations。

## 2026-08-16 — 单一默认会话，而非多会话模板化

- **背景：** 决定 `claude-guardian` 是否应当支持多个并发受监督、各自具名的 `claude` 会话（例如通过 systemd 模板单元 `claude-guardian@%i.service`）。
- **决定：** 只支持一个默认会话（`claude-code`），通过 `/etc/claude-guardian/config.env` 配置。已与用户确认。
- **驳回：** 为支持 N 个并发会话而采用 systemd 模板单元 + 逐实例配置目录——真实需求是"至少有一个始终可用"，而不是"多个始终可用"。多会话支持可以在日后出现真实需求时再添加（见 DESIGN.md 的"How to extend"）。
- **后果：** 更简单的单元文件、更简单的配置、更简单的 CLI（不需要在每个命令中都传入 `<name>` 参数）。如果运维方之后需要在同一台主机上同时运行多个 Claude 实例，再重新审视此决定。

## 2026-08-16 — tmux + systemd 双层监督，而非 screen 或自定义守护进程

- **背景：** 需求是一个 `claude` 实例既要能在主机重启后存活，也要能在 `claude` 进程本身被手动 Ctrl+C 杀掉后存活，同时还要保持可通过 SSH 远程接管的能力。
- **决定：** 使用两个相互独立的层级——systemd（`Restart=always`）监督一个 bash 循环，该循环再负责保持一个 `tmux` 会话存活，并在 `claude` 退出时重新拉起该窗格。详见 DESIGN.md → Architecture。
- **驳回：**
  - **用 `screen` 代替 `tmux`** —— screen 没有可脚本化的"这个窗口里的进程是否还活着"查询接口，不像 tmux 的 `#{pane_dead}` 格式字符串那样方便；检测一个被 Ctrl+C 杀掉的进程需要轮询 `/proc` 或解析 `screen -list`，两者都不够可靠。
  - **单层、仅靠 systemd 的设计**（直接 `ExecStart=claude`，`Restart=always`）—— 这确实会在 `claude` 退出时重启它，但运维方会在每次重启时彻底丢失交互式终端/会话（没有回滚缓冲区，也无法"重新 attach"——systemd 单元本身并不是可直接 attach 的 tty），而且没有干净的远程接管方案。
  - **自定义的 Python/Go 守护进程** —— 相比直接调用已经在每台 Debian 目标主机上现成存在的 `systemd` + `tmux`，自建守护进程没有任何有意义的优势，反而要付出构建/运行时依赖的代价。
- **后果：** 本工具同时依赖 `systemd`（假定已存在，不做检查）和 `tmux`（会被检查并由 preflight 自动安装）。安全地 detach 需要使用 tmux 前缀键，而不是 Ctrl+C——已在 DESIGN.md 和 README.md 中作为一个使用陷阱记录说明。

## 2026-08-16 — 本工具从不安装或自动认证 Claude Code CLI

- **背景：** 用户的明确指示：preflight 应当检查 `claude` 是否已安装、是否已登录，但绝不能尝试自行安装 Claude Code。
- **决定：** `claude` 是否存在是一个硬性失败的前置条件（只检查，不修复）；登录状态则按尽力而为的方式检查（查找已知的凭证文件位置），且只产生一条警告，绝不阻止启动——`claude` 自身的交互式登录流程会在运维方第一次 attach 时自然运行起来。
- **驳回：** 在 `claude` 缺失时通过 `npm i -g @anthropic-ai/claude-code` 之类的方式自动安装——这明确超出了用户要求的范围。
- **后果：** 在一台全新的、尚未安装 `claude` 的主机上，`install` 和 `run` 都会立即以一条可操作的信息明确失败，而不会代替运维方去做任何事情。
